# Deadline Assistant

Telegram-помощник, который собирает учебные дедлайны из выбранных вами чатов,
выделяет переносы и противоречия, хранит актуальные события и присылает утреннюю сводку.
Проект нужен студенту, чтобы не перечитывать учебные переписки вручную и не терять
сроки сдачи, переносы и условия досдачи. Каждый пользователь подключает свой Telegram,
выбирает чаты и получает персональные события и сводки с учётом своей учебной группы.
Основная реализация находится в `src/deadline_assistant`, модуль `deadline_bot`
добавляет CLI к тем же сервисам.

- **Архитектура и протоколы:** [анализ LLM](docs/llm-analysis.md),
  [авторизация Telegram](docs/telegram-auth.md).
- **Проверки:** [журнал проверок](docs/verification.md) и
  [отчёт о разработке](DEVELOPMENT_REPORT.md). Числа в старых разделах относятся
  к соответствующему этапу, а не к любому будущему состоянию кода.

В GitHub хранится исходный проект. `.env`, рабочая БД, Telegram-сессии, сертификаты,
логи и приватные результаты анализа туда не входят; для новой установки нужны свои

Быстрый путь после чтения разделов о ключах:

```sh
uv sync --frozen
cp .env.example .env
chmod 600 .env
# Заполните .env, сгенерируйте ключ, настройте HTTPS.
uv run alembic upgrade head
uv run python -m deadline_bot check-config
uv run python -m deadline_bot serve
```

Не перезаписывайте уже заполненный `.env` командой `cp` при обновлении.
Для запуска на своём Mac через Docker достаточно открыть `start.command`;
пошаговая инструкция и настройка локального HTTPS — в разделе 17.
Автоматические проверки и границы подтверждённой готовности описаны в
[DEVELOPMENT_REPORT.md](DEVELOPMENT_REPORT.md).

## 1. Что делает бот

Бот поддерживает несколько пользователей, отдельное подключение Telegram для каждого,
обязательное указание учебной группы и выбор групп и каналов. Один раз можно согласиться
на первый анализ до 100 последних сообщений каждого выбранного чата с ограничением
давности 90 дней либо отказаться от истории. Далее новые сообщения и изменения известных
источников анализируются ночью, а сводка отправляется утром.
Распознаются задания, экзамены, встречи, консультации, даты, переносы, отмены,
необязательные работы, условия досдачи и штрафы. Время показывается в часовом поясе пользователя.

Можно исправлять события, завершать задания, отменять собственную правку и выбирать
вариант при конфликте. Сводка и источники доступны без повторного обращения к модели.
Повторяющиеся задания можно вручную добавить в «Циклические дедлайны»: бот будет
показывать ближайший срок каждые 1–14 дней без повторного ввода и без обращения к LLM.
Бот работает через long polling: входящие webhook-запросы Bot API не требуются.

Анализируется доступный текст. Файлы, фотографии, голосовые сообщения и опросы не
распознаются. Качество понимания переписки зависит от выбранной LLM; спорные сведения
требуют решения пользователя.

## 2. Пример утренней сводки

Пример условный, его содержимое не является результатом реального анализа:

```text
📚 УЧЕБНЫЕ ДЕДЛАЙНЫ
Актуально на 20 октября 2026 · Europe/Moscow

🔴 СЕГОДНЯ
1. Физика — Лабораторная № 2
До 20 октября 2026, 18:00 · ссылка
Сдать отчёт в LMS

📅 НА ЭТОЙ НЕДЕЛЕ
2. Алгебра — Контрольная
23 октября 2026 · ссылка

🗓 В ЭТОМ МЕСЯЦЕ
3. Курсовая
30 октября 2026 · ссылка
Досдача: 31 октября 2026 — 2 ноября 2026 · Штраф: минус 10%

❔ НЕОПРЕДЕЛЁННОСТИ
4. Дискретка — Контрольная
Дата уточняется · ссылка
На следующей неделе; точный день не объявлен.
```

«ссылка» — кликабельный текст, ведущий к исходному Telegram-сообщению; превью отключено.
Без доступного URL бот пишет «ссылка недоступна», если источник сохранён.
Пустые разделы скрыты. В календаре показываются события с подтверждённой датой, включая
дату без часа. Неизвестная/приблизительная дата, существенное уточнение и нерешённый конфликт
попадают только в «Неопределённости». Отсутствие аудитории само по себе не создаёт уточнение.
Когда неопределённых событий нет, блока нет. Подробности конфликтов и выбор вариантов
доступны через «Мои дедлайны → Ещё → Уточнения» и не отправляются перед утренней сводкой.
Неделя заканчивается в воскресенье и имеет приоритет над разделом месяца; более далёкие
события попадают в «Остальное». Длинные сводки делятся на сообщения с корректной HTML-разметкой.

## 3. Как работает архитектура

Python 3.12+, aiogram 3, Telethon 1, FastAPI, SQLAlchemy async, Alembic, APScheduler 3,
Pydantic 2, OpenAI-compatible клиент к LowRouter. SQLite подходит для небольшой установки;
можно выбрать PostgreSQL. Веб-компонент, планировщик и polling работают в одном серверном процессе.

```text
Личный чат с ботом → одноразовая HTTPS-страница → зашифрованная Telethon-сессия
Выбранные чаты → новые сообщения → порции LLM → проверка операций Python
             → транзакция: события + источники + обработанные ID + checkpoint
             → конфликты и сводка из БД → личное сообщение бота
```

`SyncService` — общий анализ для кнопок бота, ночного сбора и CLI.
`CycleService` объединяет анализ и немедленную отправку. `SummaryDelivery` формирует и
доставляет одну и ту же сводку для CLI и утреннего расписания. Второй реализации анализа нет.

Перед изменением БД Python проверяет схему ответа, владельца, версии событий, допустимые
операции и ссылки на реально переданные источники. Модель не выполняет SQL и не получает
Telegram-сессию. Результат LLM сохраняется в `analysis_batches` до применения.
Хеш пакета учитывает модель, провайдера, протокол, сообщения и память. При сбое после
сохранения ответа повтор использует журнал без нового платного запроса.
Сбой между ответом провайдера и записью журнала всё ещё может потребовать повторного запроса:
у Chat Completions нет универсальной гарантии оплаты «ровно один раз».

Применение событий, отметок обработки и продвижение checkpoint происходит одной транзакцией.
Повторный запуск после ручного анализа обрабатывает новые сообщения и изменения версий,
а уже обработанные версии в LLM повторно не отправляет. Проверка короткого хвоста на правки
не означает повторного анализа всей истории. Недоступный или удалённый источник не отменяет событие.

Межпроцессные блокировки охватывают пользователя, чат, пакет, доставку и Telethon-сессию.
SQLite использует `flock` на одном локальном диске и короткие `BEGIN IMMEDIATE` транзакции;
PostgreSQL — session advisory locks и блокировки строк. Блокировки освобождаются при смерти
процесса, сервер при старте не помечает живой CLI прерванным. SQLite не следует размещать
на NFS или использовать между несколькими серверами. На PostgreSQL все процессы должны
подключаться к одной БД; для session advisory locks нужен прямой PostgreSQL или session-pooling,
а не PgBouncer в transaction-pooling.

Один polling-сервер на БД защищён отдельной блокировкой. Одновременные CLI поддерживаются;
несколько polling-серверов, `uvicorn --workers N` и горизонтальные реплики не поддерживаются.

Число пользователей в работе ограничивает `CYCLE_CONCURRENCY`, запросы модели —
`LLM_CONCURRENCY` (включая обычные CLI в других процессах). Вызовы Telegram получают
общие интервалы запросов, отправка ботом — дополнительный интервал на получателя.
Повтор временных ошибок использует backoff и учитывает FloodWait/RetryAfter.
Большая задержка Telegram переносит работу на следующий запуск вместо долгого удержания worker.
Один ошибочный пользователь не останавливает обработку других.

Журнал `analysis_runs` и JSON-логи содержат длительность, сообщения, события, конфликты,
расход входных/выходных токенов, ошибки и время последнего успешного анализа. `/status`
и «Настройки» показывают результат последнего анализа. Тарифы не зашиты; стоимость не
вычисляется без достоверного тарифа. Провайдер может не вернуть usage — тогда число неизвестно.
Логи каждого ответа LLM позволяют увидеть расход и неуспешных попыток проверки формата.

## 4. Что необходимо установить

Для локального запуска нужны Python 3.12 или новее, терминал и доступ к интернету.
Рекомендуется [uv](https://docs.astral.sh/uv/getting-started/installation/), который
устанавливает зависимости из `uv.lock`. Альтернатива — стандартные `venv` и `pip` (раздел 15).

На Mac профиль `start.command` настраивает HTTPS на `localhost` с локальным сертификатом.
Домен и отдельный сервер для этого не нужны. Ссылку входа нужно открывать на том же Mac.
Для доступа со второго устройства нужен доступный с него HTTPS-адрес (например, домен
или защищённый туннель). Сам `http://localhost:8000` позволяет проверить здоровье сервера,
но вводить Telegram-коды и пароли на HTTP приложение не разрешает даже локально.

На VPS установите Docker Engine с Compose v2, Caddy или другой reverse proxy,
настройте DNS домена на IP сервера. Порты 80/443 открываются для HTTPS-прокси;
порт БД и порт приложения публиковать наружу не нужно.

## 5. Как создать бота через BotFather

1. Откройте в Telegram официальный аккаунт [@BotFather](https://t.me/BotFather).
2. Отправьте `/newbot`.
3. Задайте отображаемое имя и уникальный username, заканчивающийся на `bot`.
4. Сохраните выданный токен в менеджере секретов или непосредственно в `.env`.
5. Откройте ссылку на своего бота и отправьте `/start` после запуска приложения.

Никому не пересылайте токен. Для этой схемы работы не добавляйте бота во все учебные
группы: историю читает подключённый аккаунт пользователя через Telethon.

## 6. Где взять TELEGRAM_BOT_TOKEN

Это токен, выданный BotFather для вашего бота. Если бот уже существует, выберите его
через `/mybots` и откройте управление API-токеном. Вставьте значение после `=`:

```dotenv
TELEGRAM_BOT_TOKEN=
```

В примерах реального токена нет. При утечке отзовите его через BotFather и замените в
окружении. Не вставляйте токен в URL терминальных команд, которые могут попасть в историю.
Один Bot Token даёт доступ к боту, а не ко всем чатам вашего личного аккаунта.

## 7. Где получить Telegram API ID и API hash

Откройте [my.telegram.org](https://my.telegram.org), авторизуйтесь своим аккаунтом,
перейдите в **API development tools**, создайте приложение и сохраните `api_id` и `api_hash`.
Заполняйте сведения о приложении достоверно. Доступность регистрации и ограничения
определяет Telegram.

```dotenv
TELEGRAM_API_ID=
TELEGRAM_API_HASH=
```

`TELEGRAM_API_ID` — положительное целое число, hash — секретная строка.
Код входа на my.telegram.org вводится на сайте Telegram, а не в чат Deadline Assistant.

## 8. Для чего нужны API ID и API hash

Они идентифицируют ваше клиентское приложение в MTProto API. Telethon использует их
вместе с отдельной сессией авторизованного пользователя. Бот-токен этого не заменяет.
Каждый пользователь явно подключает собственный аккаунт и выбирает доступные ему чаты.
Приложение проверяет совпадение аккаунта, подключаемого через браузер, с владельцем чата бота.
Доступ к чужим и недоступным подключённому аккаунту чатам не появляется.

## 9. Как зарегистрироваться в LowRouter

Откройте [LowRouter](https://lowrouter.ru) и следуйте регистрации на сайте.
После входа ознакомьтесь с условиями обработки данных и тарификацией, при необходимости
пополните баланс и настройте доступные ограничения расходов.

Официальная последовательность подключения и адрес API приведены в
[быстром старте LowRouter](https://lowrouter.ru/docs/getting-started/).
Интерфейс кабинета может меняться; проект не требует установки отдельного приложения LowRouter.

## 10. Где получить LOWROUTER_API_KEY

В личном кабинете LowRouter откройте раздел **API-ключи** и создайте отдельный ключ для
Deadline Assistant. Сохраните его в `.env`:

```dotenv
LOWROUTER_API_KEY=
LLM_BASE_URL=https://api.lowrouter.ru/v1
```

При утечке отзовите ключ в кабинете. Платный API требует контроля расходов:
первый анализ 20 чатов по 100 сообщений может сделать много запросов. Сначала подключите
один небольшой чат, посмотрите usage и расходы в кабинете. Dry-run тоже вызывает настоящий
API, если не подменить интеграцию тестовым мок-объектом.

## 11. Как выбрать модель

Укажите точный идентификатор модели из актуального каталога своего провайдера.
В `.env.example` запрошено значение `LLM_MODEL=gpt-6-luna`; наличие этой модели,
цену и её качество необходимо проверить в своём кабинете. Название по умолчанию не
является гарантией доступности.

Модель должна поддерживать `/chat/completions` и возвращать валидные операции.
Адаптер начинает с `json_schema`, при явно неподдерживаемом формате пробует `json_object`,
затем text с обязательной проверкой JSON в Python. Можно задать
`LLM_STRUCTURED_OUTPUT=false` или `LLM_JSON_MODE=false` для совместимого провайдера.

Вход ограничивается `LLM_MAX_INPUT_TOKENS`, выход — `LLM_MAX_OUTPUT_TOKENS`.
Значение входа должно оставлять место под выход и служебные токены в реальном контексте
модели. Например, для окна 32k разумно уменьшить входной бюджет относительно примера 30k,
если выход допускает 6k. Для известных GPT-моделей вход считается токенизатором `tiktoken`;
для неизвестных моделей остаётся консервативная верхняя оценка по UTF-8. Учитываются
полные инструкции, схема и память, исходные сообщения и ошибки повторной проверки.
Слишком большой пакет разбивается рекурсивно; конец чата не теряется и тексты не обрезаются.
Одно сообщение или память, которые не помещаются даже отдельно, останавливают порцию с
понятной ошибкой и сохраняют checkpoint перед ней. Увеличьте бюджет или разберите накопленные
события; уменьшение лимита памяти не даёт права молча пропускать актуальные события.

## 12. Куда вставлять все значения

Основной источник конфигурации — файл `.env` в корне проекта. Его читает Pydantic Settings;
переменные настоящего окружения имеют приоритет. Не нужно редактировать Python-файлы.
В production можно передавать окружение из менеджера секретов без файла.

| Переменная | Откуда / значение |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | BotFather |
| `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` | my.telegram.org/apps |
| `LOWROUTER_API_KEY` | API-ключи LowRouter |
| `LLM_BASE_URL`, `LLM_MODEL` | API и каталог выбранного провайдера |
| `DATABASE_URL` | SQLite по умолчанию либо закрытый PostgreSQL |
| `SESSION_ENCRYPTION_KEY` | Локально сгенерированный Fernet-ключ |
| `PUBLIC_BASE_URL` | Публичный HTTPS origin вашего приложения |
| `DEFAULT_TIMEZONE` | Например `Europe/Moscow` |
| `DAILY_SYNC_HOUR`, `DAILY_DIGEST_HOUR` | По умолчанию 2 и 8, местные часы пользователя |
| `INITIAL_MESSAGE_LIMIT` | До 100 последних сообщений каждого чата при однократном первом анализе |
| `MESSAGE_MAX_AGE_DAYS` | 90 дней: максимальная давность сообщений для анализа |
| `LLM_TOKEN_ENCODING` | Необязательная кодировка оценки входа, например o200k_base |

Для совместимости старые `BOT_TOKEN` и `LLM_API_KEY` продолжают работать как псевдонимы.
Используйте новые имена; не задавайте одновременно оба варианта. Для расписания с минутами
поддерживаются прежние `NIGHT_SYNC_TIME=02:30` и `DEFAULT_DIGEST_TIME=08:15`:
в таком случае удалите соответствующие `DAILY_SYNC_HOUR`/`DAILY_DIGEST_HOUR`, потому что
явно заданные часы имеют приоритет. Изменение времени по умолчанию относится к новым профилям;
существующий пользователь меняет утреннее время через `/settings`.

## 13. Как правильно создать .env из .env.example

Из корня проекта, только при первой установке:

```sh
cp .env.example .env
chmod 600 .env
```

Откройте `.env` текстовым редактором. Каждая настройка занимает одну строку `ИМЯ=значение`.
Уберите пустые значения обязательных секретов, заменив их настоящими, без лишних пробелов.
Установите `PUBLIC_BASE_URL=https://ваш-домен` до включения Bot Token.
Не публикуйте `.env` в Git, скриншотах, задачах и логах. `.gitignore` и `.dockerignore`
исключают его, но это не защищает от ручной отправки.

После правки перезапустите сервер. В Compose окружение существующего контейнера обновляется
командой `docker compose up -d --force-recreate app`, а не простым `restart`.
Опция CLI `--env-file /защищённый/путь` задаётся перед именем команды.

## 14. Как сгенерировать ключ шифрования сессий

После установки зависимостей:

```sh
uv run python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
```

Перенесите результат в `SESSION_ENCRYPTION_KEY` и сохраните отдельно от резервной копии
БД. Это не Telegram-пароль и не токен бота. Не генерируйте новый ключ при каждом рестарте.
Если ключ потерян, сохранённые сессии не расшифруются: пользователям нужно подключиться заново.
Если ключ скомпрометирован, отзовите Telegram-сессии и проведите переподключение с новым ключом.
Шифрование сессий не шифрует остальные таблицы — защитите диск и резервные копии.

## 16. Как запустить миграции

Сначала проверьте `DATABASE_URL` и сделайте копию существующей БД. При обновлении остановите
сервер и активные CLI, затем:

```sh
uv run alembic upgrade head
uv run alembic current
uv run alembic check
```

Миграции 0001–0005 сохраняют существующие события и подключения. Alembic использует только
настройку БД: отсутствие ключей Telegram/LLM не мешает миграциям.
`alembic check` должен сообщить об отсутствии новых операций.
Не удаляйте БД для исправления ошибки миграции. Восстановление описано в разделе 30.
При смене SQLite на PostgreSQL команда создаёт схему, но не переносит данные между СУБД.

## 17. Как запустить приложение

**На своём Mac с Docker Desktop:**

1. В Finder откройте папку проекта и дважды щёлкните `start.command`.
2. Дождитесь запуска Docker Desktop и сборки. При первом запуске macOS может попросить
   разрешить доверие к сертификату `Deadline Assistant localhost` в вашей связке ключей.
   Это разрешение macOS; Telegram-пароль в Terminal не вводится.
3. Дождитесь сообщения «Бот запущен в Docker».
4. Откройте своего бота в Telegram **на этом Mac** и отправьте `/start` или `/connect`.
   Скопируйте одноразовую ссылку из сообщения целиком и откройте её в браузере этого же Mac.
   Адрес начинается с `https://localhost:8443/connect#token=`. Telegram не принимает localhost
   в URL-кнопках, поэтому локальная ссылка присылается текстом для копирования.
5. Выберите учебные чаты и запустите первый анализ.

До подключения аккаунта доступны подключение, настройки и помощь. Команды дедлайнов,
действия в старых сообщениях и фоновая рассылка сводок требуют действующего подключения.

Платный сервер, домен и HTTPS-туннель для этого сценария не нужны. Docker запускает
приложение на вашем компьютере. Для стабильной работы Mac должен быть включён и не спать.
Ссылка localhost, открытая на телефоне, указывает на сам телефон и не подключит его к Mac.

`start.command` использует отдельный `compose.macos.yaml`: он переопределяет
PUBLIC_BASE_URL на HTTPS **внутри контейнера**, не переписывая `.env` и ваши ключи.
Профиль использует существующий файл `data/deadline.db` на Mac. Перед миграциями
создаётся копия в `data/backups`. Файлы доступны тому же непривилегированному UID пользователя,
который запустил скрипт. TLS завершается непосредственно приложением, поэтому reverse proxy
для этого локального варианта не нужен. Порт 8443 опубликован только на 127.0.0.1.

Локальный сертификат — сертификат сервера, а не CA: он не может выпускать сертификаты
для других сайтов. Доверие в пользовательской связке ключей ограничено политикой SSL и
именем localhost. Срок — 90 дней; при следующем запуске сертификат обновится, если до
окончания останется менее недели. Ключ лежит в `data/local-tls` с правами 600 и не входит
в образ/Git. Для удаления доверия используйте «Связку ключей» и найдите
`Deadline Assistant localhost` или `security remove-trusted-cert data/local-tls/localhost.crt`.
Не удаляйте весь каталог data: в нём также находится БД.

Для остановки дважды щёлкните `stop.command`. Он штатно остановит только контейнер
этого проекта и сохранит данные. Закрытие Terminal и Ctrl+C прекращают **показ журналов**;
сам контейнер продолжает работать до stop. Повторное нажатие start не создаёт второй экземпляр.
Если macOS предлагает выбрать приложение для `.command`, выберите Terminal; при ограничении
Gatekeeper используйте «Открыть» из контекстного меню Finder.

Для старта/остановки из терминала можно использовать
`python3 scripts/macos_docker.py start` и `python3 scripts/macos_docker.py stop`.
Нужен Python 3.9+ для вспомогательного скрипта; само приложение работает на Python 3.12
в Docker. В этой установке также можно использовать `.venv/bin/python` для скрипта.
Для разовой команды CLI откройте Exec у запущенного контейнера в Docker Desktop и
выполните, например, `python -m deadline_bot run-cycle --all --send-now`.

Автоматические копии в `data/backups` периодически переносите в защищённое хранилище
и удаляйте по своей политике хранения. Для VPS используйте основной Compose из раздела 27;
`compose.macos.yaml` предназначен для локальной SQLite на Mac.

Без Docker:

```sh
uv run python -m deadline_bot check-config
uv run python -m deadline_bot serve
```

Прежняя команда `uv run deadline-assistant` поддерживается. Приложение запускает веб-сервер,
бота и планировщик. Остановить его можно `Ctrl+C`. На сервере без Docker используйте отдельного
непривилегированного пользователя и systemd с `Restart=on-failure`, `UMask=0077`,
`WorkingDirectory` корня проекта и `ExecStart` из вашей `.venv`.

Без внешних ключей `serve` позволяет проверить веб-компонент после миграций;
`check-config` вернёт код 3 и перечислит недостающие настройки. Это ожидаемо, не полный рабочий режим.

```sh
curl --fail http://127.0.0.1:8000/health/live
curl --fail http://127.0.0.1:8000/health/ready
```

`live` проверяет процесс, `ready` — доступность БД и polling. При старте проверяется версия
схемы. Проверка не доказывает реальную работоспособность ключа LowRouter или сертификата.
Проверить страницу можно на `/connect`, но вход требует действующей ссылки из бота.

## 18. Как подключить Telegram-аккаунт через бота

1. Откройте личный чат с вашим ботом и отправьте `/start`.
2. Нажмите «Подключить аккаунт» под сообщением.
3. Откройте одноразовую HTTPS-ссылку, действующую 10 минут.
4. Сверьте номер заявки на странице и в боте. Нажмите «Это я» только для своей заявки.
5. Выберите QR-вход со второго устройства или ввод номера на HTTPS-странице.
6. Для QR: Telegram → Настройки → Устройства → Подключить устройство.
7. Для одного телефона: введите номер на странице, получите код выбранным Telegram способом,
   вернитесь на страницу и введите его там. При необходимости введите 2FA-пароль там же.
8. Дождитесь сообщения «Аккаунт успешно подключён» и перейдите к «Мои чаты».

Нельзя отправлять коды Telegram, пароль 2FA или StringSession в переписку с ботом.
Обычный Bot API не даёт доступа к личным чатам. Для чтения используется Telethon с вашим
явным входом. SMS не гарантируется; Telegram сам выбирает канал доставки кода.
Подключаемый аккаунт должен совпадать с аккаунтом, открывшим бота.

Если страница указывает доставку в приложение Telegram, проверьте служебный чат «Telegram»
на устройствах с уже открытым аккаунтом, включая архив. SMS в этом случае не отправляется.
Кнопка «Код не пришёл — запросить ещё раз» появляется только при предложенном Telegram
поддерживаемом следующем способе доставки (SMS/звонок) и становится доступна после его
таймера. Нажмите её вручную; автоматической повторной отправки нет. Если повторный запрос
недоступен и кода нет, отмените вход, получите новую ссылку в боте и используйте QR со
второго устройства. Работа QR не подтверждает доставку кода по телефону.

Ссылка содержит токен во фрагменте `#token=`, который браузер не передаёт HTTP-серверу.
Страница обменивает его POST-запросом, очищает адрес, использует Secure/HttpOnly cookie,
SameSite=Strict, проверку Origin и CSRF. Подробности: [docs/telegram-auth.md](docs/telegram-auth.md).

Первоначальная настройка проходит строго по порядку: `/start` → подключение своего
Telegram-аккаунта → указание учебной группы, например `БПИ267`. До подключения аккаунта
доступна кнопка подключения; после подключения бот просит группу без рабочего меню.
Группа обязательна: `/cancel`, рабочая команда и старая кнопка не позволяют пропустить её.
Только после сохранения группы открываются чаты, дедлайны и настройки расписания.
Группа передаётся ИИ для выбора подходящих дат из распределений. Изменить её позже можно
через «Настройки → Учебная группа».

Все кнопки бота находятся под сообщениями. Главное меню содержит «Мои дедлайны»,
«Циклические дедлайны», «Мои чаты» и «Настройки»; из вложенных разделов есть возврат в главное меню. При `/start`
старая клавиатура у поля ввода скрывается. В меню команд Telegram при старте сервера
публикуется только `/start`. Списка Help и команды `/sync` больше нет. Остальные прежние
команды сохранены как совместимые алиасы, но для обычной работы достаточно кнопок.
Контакт поддержки владелец указывает отдельно в описании бота.

## 19. Как выбрать отслеживаемые чаты

Откройте «Мои чаты». Доступны поиск, страницы, отметки выбора и обновление
каталога. Отметьте учебные группы и каналы и нажмите «Сохранить».
До сохранения выбор остаётся черновиком. Недоступный другому пользователю чат нельзя
подключить подстановкой ID. Приватные группы не обязаны иметь публичный username.

«Подключения» показывают текущее состояние; кнопка «Отключить» отключает один чат.
После отключения его сообщения больше не читаются, уже извлечённые дедлайны сохраняются.
Утрата доступа к каналу требует проверить членство и обновить каталог.

После первого сохранения непустого выбора бот спрашивает, анализировать ли старые сообщения.
После сделанного выбора новые и повторно подключённые чаты отслеживаются с момента
подключения: повторного предложения разобрать историю и немедленного анализа нет.

## 20. Как работает однократный первый анализ 100 сообщений

Вопрос «Проанализировать старые сообщения выбранных чатов?» имеет два ответа:

- «Да» — один раз создать фоновое задание и разобрать до `INITIAL_MESSAGE_LIMIT=100`
  последних доступных сообщений каждого выбранного чата. Бот остаётся отзывчивым.
- «Нет» — не запускать анализ сейчас и отслеживать сообщения с момента отказа;
  старая переписка не попадёт в последующий ночной анализ.

Решение сохраняется в БД. Повторные `/start`, переподключение аккаунта, старые кнопки,
ошибка или остановка задания не возвращают право ручного запуска. После любого ответа
анализ выполняется только ночью, сводка отправляется утром. Команды `/sync` и кнопки
повторного запуска в боте нет. Значение `INITIAL_MESSAGE_LIMIT` по умолчанию и его потолок — 100;
прежнее значение 1000 в `.env` автоматически ограничивается до 100, сам файл не меняется.
Профили с запусками до обновления считаются уже использовавшими первый анализ.

Telegram не гарантирует доступность скрытой или удалённой истории.
В ИИ передаются сообщения за последние `MESSAGE_MAX_AGE_DAYS=90` дней; старые
пропускаются с сохранением checkpoint, даже если в чате мало сообщений. Проверка
уже известных источников по ID не ограничена этим окном. Полностью прошедшие
новые события не сохраняются, а старая дата с пометкой «требует уточнения» больше
не удерживается в сводке. Досдача и события без даты учитываются отдельно.

Сообщения упорядочиваются по ID и анализируются порциями `SYNC_BATCH_SIZE=50`; слишком
большие порции дополнительно делятся по бюджету контекста. Верхняя граница первоначальной
истории сохраняется, поэтому сбой не сдвигает произвольно выбранное начальное окно.
Каждая успешная порция фиксирует checkpoint. `SYNC_TIMEOUT_SECONDS=600` ограничивает
время без прогресса: после сохранения порции отсчёт начинается заново. Поэтому большая
история может обрабатываться по частям, пока порции продолжают сохраняться.
Ограничение действует и при делении по контексту, проверке источников и обработке
сохранённых исправлений. Если текущая порция зависла, анализ останавливается;
следующий ночной анализ продолжит с сохранённого checkpoint без дубликатов.
«Настройки» показывают последний анализ и его состояние.
Бот также присылает прогресс каждые `ANALYSIS_PROGRESS_INTERVAL_SECONDS=120` секунд,
не вызывая ИИ. `/stop_sync` останавливает фоновое задание и сохраняет уже применённые
порции. Отменённый внешний запрос мог быть уже оплачен провайдером.

Один запуск имеет мягкие пределы: `SYNC_MAX_DURATION_SECONDS=300` секунд и
`SYNC_MAX_TOTAL_TOKENS=100000` токенов по полученным ответам провайдера. Текущая
порция завершается и сохраняется, после чего анализ получает статус «обработана
часть истории» и бот присылает сводку. Следующий ночной анализ продолжает с checkpoint.
Временной предел проверяется между порциями, поэтому запуск может быть длиннее
пяти минут на время текущего запроса. Лимит токенов проверяется перед следующей
порцией истории; текущая порция и её ограниченные попытки могут превысить его.
Это ограничение объёма, а не точный денежный бюджет: тарифы задаёт провайдер.
Таймауты, обрывы связи и HTTP 5xx не повторяются автоматически: первый запрос мог
продолжить выполняться и быть оплаченным. `LLM_MAX_RETRIES` ограничивает только
повторы явных отказов 429; `LLM_FORMAT_RETRIES` — исправления формата полученного ответа.
При ошибке после успешных порций бот также отправляет сохранённую сводку.
После успеха бот присылает результат задания и сводку.

Последующие ночные запуски и CLI читают сообщения после checkpoint, проверяют ограниченный хвост
на редактирование и заново проверяют сохранённые активные источники по ID.
Обычные тексты остаются только в памяти анализа. В БД сохраняются тексты подтверждающих
источников, метаданные и хеши обработанных версий, а не полная переписка.

## 21. Как проверить утренние уведомления

Убедитесь, что бот не заблокирован и `/settings` показывает нужный часовой пояс и время.
Сначала отправьте текущую сводку без платного анализа:

```sh
uv run python -m deadline_bot send-summary --user 123456789
```

Число замените своим Telegram user ID; это ID пользователя, не username и не ID бота.
Его можно получить средствами Telegram/API, которым вы доверяете.
Затем настройте ближайшее будущее время через `/settings Europe/Moscow 10:45`, оставьте
сервер работающим и проверьте доставку. Верните желаемое время после проверки.

Ночной сбор по умолчанию в 02:00, сводка в 08:00. Проверка расписания выполняется каждую
минуту. Ночной сбор и его повторы запускаются только в течение часа после назначенного
времени (по умолчанию 02:00–03:00). При дневном рестарте пропущенный сбор ждёт следующей ночи.
До подключения аккаунта, указания группы и ответа «Да / Нет» расписание не выполняется.
Сводка догоняется в пределах `DIGEST_CATCHUP_HOURS=6`, более поздняя помечается пропущенной,
чтобы не присылать утром прошлого дня ночью. Дата задачи хранится в БД; повторный tick и
переход часового пояса на зимнее время не создают второй ежедневный дайджест.

После временной ошибки доставка продолжается с первой неподтверждённой части. Telegram
Bot API не поддерживает ключ идемпотентности отправки: при аварии сразу после отправки
и до фиксации квитанции одна часть может повториться. Это доставка «как минимум один раз».

## 22. Как разработчику вручную запустить анализ в любое время

Из корня проекта:

```sh
uv run python -m deadline_bot run-cycle --all --send-now
uv run python -m deadline_bot run-cycle --all --announce "Сейчас запустим внеплановый тестовый анализ." --send-now
uv run python -m deadline_bot run-cycle --user 123456789 --send-now
uv run python -m deadline_bot run-cycle --all --dry-run
uv run python -m deadline_bot send-summary --user 123456789
uv run python -m deadline_bot check-config
uv run python -m deadline_bot test-llm
```

Без `--send-now` цикл только обновляет данные. `--all` выбирает активные профили с
подключённой Telegram-сессией, сохранённой группой и сделанным выбором первого анализа.
`--user` обозначает Telegram user ID и позволяет оператору выбрать профиль явно. Ошибка одного профиля
выводится отдельно, остальные продолжают работу. Настройки и конфигурация проверяются
до внешних вызовов. Это эксплуатационная возможность разработчика с доступом к серверу;
в боте ручного аналога нет. Команды не запускаются автоматически при изменении кода.

`--announce "Текст"` сначала отправляет предупреждение всем выбранным пользователям,
и только после успешной отправки всех предупреждений начинается обработка. Если отправка
предупреждения завершилась ошибкой, анализ не начинается. `--send-now` отправляет результат
после обработки; без него результат попадёт в очередную утреннюю сводку. Предупреждение
несовместимо с `--dry-run` и требует настроенного токена бота.

Dry-run делает согласованную копию данных только выбранного пользователя во временную
приватную SQLite-базу и запускает обычный сервис анализа там. Основная БД открывается
для чтения, checkpoint, события, источники, журналы и статусы не меняются. Предложения
печатаются в терминал; Telegram-уведомления не отправляются. Запросы к Telegram/LLM
реальные, если вы запускаете команду с настоящими ключами, и могут стоить денег.
Временные файлы удаляются при нормальном завершении. Dry-run использует отдельный журнал
ответов и лимиты, не прогревает основной платёжный кеш; его следующий обычный запуск
может повторно оплатить анализ. Не публикуйте вывод: там есть извлечённые учебные данные.

```sh
uv run python -m deadline_bot --help
uv run python -m deadline_bot run-cycle --help
uv run python -m deadline_bot send-summary --help
uv run python -m deadline_bot check-config --help
uv run python -m deadline_bot test-llm --help
```

| Код завершения | Значение |
| --- | --- |
| 0 | Команда успешно завершена; для пустого `--all` также 0 |
| 2 | Ошибка аргументов или неизвестный пользователь |
| 3 | Неверная/неполная конфигурация, неготовая БД при check-config |
| 4 | Хотя бы один пользователь завершился с ошибкой в массовом цикле |
| 5 | Общая ошибка исполнения, сети, БД или интеграции |
| 130 | Прерывание пользователем |

`test-llm` делает небольшой платный запрос через тот же адаптер, проверяет формат ответа
и выводит usage. Он не читает чаты и не отправляет результат ботом. Успех не гарантирует
качество распознавания всех реальных дедлайнов. `send-summary` читает сохранённые события
и не вызывает модель, даже если ключ LLM отсутствует.

## 23. Как работает редактирование дедлайнов

Откройте «Мои дедлайны», нажмите «Редактировать дедлайн», выберите событие кнопкой или
ответом на конкретный список. В сводке также есть «Завершить задание»; источники,
отмена исправления, уточнения и обновление сохранённой сводки доступны через «Ещё».
Можно изменить поле напрямую или написать свободный текст: «Срок перенесли на 12 ноября».
Текстовое исправление сначала сохраняется, затем сразу анализируется; при сбое API остаётся
ожидающим следующего цикла. `/correct UUID текст` делает то же.

UUID и версия привязаны к неизменяемому списку выбора. Номер из старого списка не
переназначается другому событию. `/done UUID` и кнопка завершения сохраняют пользовательское
выполнение; следующий анализ автоматически его не отменит. `/undo UUID` отменяет последнее
собственное исправление без LLM, если после него не появилась новая информация.
Кнопка «Отмена» отменяет многошаговое меню. Просмотр дедлайнов, источников и «Обновить сводку»
не тратят запросы модели. Для событий из переписки дата без времени остаётся без часов.

### Циклические дедлайны

Откройте «Циклические дедлайны» в главном меню или под сводкой и добавьте задание:
название → интервал от 1 до 14 дней → первый ближайший срок → время → подтверждение.
Интервал и день недели выбираются кнопками; конкретную дату можно ввести вручную.
В мастере доступны «Назад» и «Отмена»: до подтверждения изменения не сохраняются.

Например, во вторник выберите понедельник и интервал 7 дней — первый срок будет
в ближайший понедельник, следующие — каждый понедельник. Интервал 14 дней означает
раз в две недели, 1 день — ежедневно. Если сегодняшний выбранный час уже прошёл,
при выборе дня недели будет предложена следующая неделя; прошедшую конкретную дату
мастер не принимает.

Время ЧЧ:ММ относится к вашему часовому поясу, который показан в мастере. Кнопка
«Без времени» устанавливает **23:59 МСК** выбранного дня, даже если в настройках
профиля указан другой пояс. Карточка показывает точную дату и пояс; общая сводка
отображает срок в текущем поясе профиля.

В карточке есть два отдельных действия:

- **«Закрыть»** — завершить только показанное повторение. До его срока оно остаётся
  в общей сводке зачёркнутым. После срока появится следующее активное повторение.
- **«Закончить отслеживание»** — отключить всю серию после подтверждения. Она больше
  не появляется ни в списке отслеживаемых серий, ни в сводках.

Повторения привязаны к первому сроку и интервалу. Досрочное закрытие не сдвигает график,
а пропущенные сроки не накапливаются: после перерыва бот показывает ближайший будущий.
Изменить название, период и первый срок можно из карточки серии. Циклические дедлайны
сохраняются в БД и продолжаются после перезапуска; их создание и управление не вызывают LLM.

Перед запуском обновлённой версии выполните миграцию `alembic upgrade head`
до `h108_recurring`, предварительно создав резервную копию рабочей БД по разделу 29.

## 24. Как разрешать конфликты

Откройте «Мои дедлайны → Ещё → Уточнения». Бот показывает старое состояние и
подготовленные альтернативы, тексты и доступные ссылки на источники. Нажмите «Вариант N»
либо отправьте `/resolve UUID_КОНФЛИКТА номер`. `0` оставляет сведения неподтверждёнными.
Можно выбирать не только два варианта; поддерживаются сохранённые варианты 3 и далее.

Выбор обновляет БД и сразу присылает сводку без LLM. Если версия события изменилась,
старый выбор не перезаписывает новые сведения. «Проверить снова» явно вызывает новый анализ.
Неизвестная роль автора остаётся `unknown`; права администратора группы сами по себе не
означают, что человек — преподаватель. Python не может доказать истинность утверждения из переписки.

## 25. Как поменять LLM-модель

Измените `LLM_MODEL`, при смене провайдера также `LLM_BASE_URL` и `LOWROUTER_API_KEY`.
Перезапустите приложение и выполните `test-llm` (раздел 22).
Сначала проверьте один чат через dry-run, помня о цене. Изменение модели само по себе не
перечитывает уже обработанную историю и не обнуляет checkpoint. Не удаляйте курсор
для эксперимента в основной БД: используйте отдельную тестовую установку.

## 26. Как изменить расписание

`DEFAULT_TIMEZONE=Europe/Moscow`, `DAILY_SYNC_HOUR=2`, `DAILY_DIGEST_HOUR=8` задают
начальные настройки. Пользователь может выбрать IANA-пояс и время утренней сводки в
«Настройках», например `/settings Asia/Yekaterinburg 08:30`.
Часы ночного сбора общие, но интерпретируются в часовом поясе каждого пользователя.

После изменения окружения нужен рестарт. Существующие настройки профиля не стираются.
Время в БД хранится в UTC. При временном отсутствии ИИ сводка показывает последние
сохранённые данные с предупреждением об их возможном устаревании.

## 27. Как запустить на Linux VPS через Docker Compose

1. Установите Docker Engine, Compose v2 и Caddy по официальным инструкциям своей ОС.
2. Разместите проект в отдельном каталоге, настройте `.env` и ключ шифрования.
3. В DNS направьте домен на VPS, установите `APP_ENV=production` и
   `PUBLIC_BASE_URL=https://deadline.example.org`, заменив домен своим.
4. Настройте reverse proxy и точные адреса `FORWARDED_ALLOW_IPS`.
5. Сделайте резервную копию, если БД уже существует, остановите CLI/сервер перед миграцией.
6. Запустите:

```sh
docker compose -f docker-compose.yml up -d --build
docker compose -f docker-compose.yml logs -f app
docker compose -f docker-compose.yml exec app python -m deadline_bot check-config
```

Файл `compose.yaml` сохранён для совместимости и совпадает с `docker-compose.yml`.
При наличии обоих `docker compose` обычно выбирает `compose.yaml`; можно явно указывать
`-f docker-compose.yml`, как выше. Не меняйте только один из двух файлов.
Entrypoint при обычном запуске применяет миграции и запускает сервер. Для CLI используйте:

```sh
docker compose exec app python -m deadline_bot run-cycle --all --send-now
docker compose exec app python -m deadline_bot send-summary --user 123456789
```

БД и блокировки сохраняются в именованном томе `deadline_data`, путь внутри — `/app/data`.
Контейнер работает от UID/GID 10001, с read-only корнем и временным `/tmp`.
`SYNC_TIMEOUT_SECONDS` задаёт максимум простоя, а не общую длительность обработки истории.
`stop_grace_period` должен оставлять время на штатную остановку и сохранение текущей
порции; при увеличении таймаутов учитывайте этот запас. Рестарт — `unless-stopped`.
Логи ротируются по 10 МБ, максимум 3 файла. Healthcheck обращается к `/health/ready`.
Unhealthy требует проверки; Docker сам по одному лишь unhealthy не пересоздаёт контейнер.
При неожиданной остановке polling приложение штатно завершает процесс с кодом 5,
после чего `unless-stopped` или systemd могут его перезапустить.

Пример Caddy на хосте, файл [deploy/Caddyfile.example](deploy/Caddyfile.example):

```caddyfile
deadline.example.org {
    reverse_proxy 127.0.0.1:8000
}
```

Caddy получает и продлевает сертификат при правильных DNS и доступных 80/443.
Access log не включён. Не включайте журналирование тел POST-запросов на прокси.
Порт приложения привязан только к `127.0.0.1` на хосте. `FORWARDED_ALLOW_IPS` должен
содержать IP прокси **как его видит контейнер**, часто адрес bridge gateway, а не loopback хоста.
Узнать gateway можно через `docker inspect` контейнера. Это доверенная конфигурация
конкретного сервера; не заменяйте её на `*`. Иначе вход может получить HTTP 426 или
недоверенный клиент сможет подставить forwarded-заголовки. Проверяйте HTTPS с внешнего браузера.

Для PostgreSQL задайте случайный `POSTGRES_PASSWORD` из букв/цифр в `.env`
(например, результат `python -c 'import secrets; print(secrets.token_hex(32))'`) и выполните:

```sh
docker compose -f docker-compose.yml -f compose.postgres.yaml up -d --build
```

PostgreSQL хранится в `postgres_data`, имеет healthcheck и не публикует порт на хост.
Не включайте в firewall доступ к 5432 из интернета. При внешнем PostgreSQL используйте
частную сеть и TLS по политике сервера. Реальный PostgreSQL требует отдельной проверки на VPS.

## 28. Как обновлять приложение

Сохраните БД и ключи. Остановите приложение и активные CLI. Получите новую версию файлов
из своего источника (Git или архив), сохранив `.env` и volumes. Сверьте новые настройки
с `.env.example`, не копируя пример поверх секретов.

Без Docker: `uv sync --frozen`, `uv run alembic upgrade head`, `uv run alembic check`,
затем запустите сервер и `check-config`.
С Docker: `docker compose stop app`, затем `docker compose up -d --build app`.
Entrypoint выполнит миграции. Проверьте логи, healthcheck, авторизацию и ручную сводку.
Не запускайте миграции одновременно из нескольких процессов; блокировки рабочих задач
не заменяют отдельное окно миграций. При ошибке сохраните диагностику без секретов и
восстановите совместимую версию кода вместе с резервной копией.

## 29. Как делать резервную копию

SQLite в WAL-режиме нельзя надёжно копировать только одним `cp data/deadline.db`
во время работы. Используйте SQLite backup API:

```sh
uv run python scripts/backup_sqlite.py data/deadline.db backups/deadline-2026-10-20.sqlite
```

Скрипт создаёт согласованную копию, проверяет `integrity_check` и ставит права 600.
Имя файла меняйте при каждом запуске; существующий файл по умолчанию не перезаписывается.

В Docker сначала создайте копию в томе, затем скопируйте её на хост:

```sh
docker compose exec app python scripts/backup_sqlite.py /app/data/deadline.db /app/data/backups/backup.sqlite
mkdir -p backups
chmod 700 backups
docker compose cp app:/app/data/backups/backup.sqlite backups/backup.sqlite
chmod 600 backups/backup.sqlite
```

Для последующих копий выбирайте другие имена. Сохраните `.env` и особенно ключ шифрования
в отдельном защищённом месте, зашифруйте резервные копии и ограничьте срок хранения.
Копии содержат личные данные. Старые копии не очищаются автоматически при `/delete_data`.

Для PostgreSQL используйте `pg_dump` совместимой версии и сохраните результат отдельно от
тома. Например, в закрытой Compose-установке:

```sh
docker compose -f docker-compose.yml -f compose.postgres.yaml exec -T postgres pg_dump -U deadline -d deadline -Fc > backups/deadline.dump
chmod 600 backups/deadline.dump
```

Создайте каталог `backups` заранее. Проверяйте восстановление копии в отдельной установке.

## 30. Как восстановить данные

Остановите сервер и все CLI, сохраните дополнительную копию текущей БД и убедитесь, что
резервная копия соответствует нужной установке. Для локальной SQLite:

```sh
uv run python scripts/backup_sqlite.py backups/deadline-2026-10-20.sqlite data/deadline.db --replace
uv run alembic upgrade head
uv run python -m deadline_bot check-config
uv run python -m deadline_bot serve
```

`--replace` явно разрешает замену БД. Нельзя восстанавливать поверх работающего приложения.
Верните соответствующий `SESSION_ENCRYPTION_KEY` из отдельного хранилища.

Для Docker сначала передайте файл в отдельный путь тома, пока контейнер работает:

```sh
docker compose exec -T app python -c 'from pathlib import Path; import sys; p=Path("/app/data/restore.sqlite"); p.write_bytes(sys.stdin.buffer.read()); p.chmod(0o600)' < backups/backup.sqlite
docker compose stop app
docker compose run --rm --no-deps app python scripts/backup_sqlite.py /app/data/restore.sqlite /app/data/deadline.db --replace
docker compose up -d app
```

Последний обычный запуск применит миграции. `docker compose run` с явно переданной командой
не запускает polling и не применяет миграции автоматически. Не используйте `down -v`:
эта команда удаляет сохраняемые volumes. Для PostgreSQL остановите app и используйте
`pg_restore` в заранее подготовленную закрытую БД; параметры очистки и замены выбирайте
после проверки резервной копии, поскольку они могут удалить существующие таблицы.

## 31. Как отключить аккаунт и удалить данные

«Настройки → Аккаунт → Отключить аккаунт» удаляет локальные Telegram-сессии и ссылки входа, отключает чаты
и пытается отозвать авторизацию Telegram. Дедлайны при этом сохраняются.
Если отзыв не подтверждён, откройте Telegram → Настройки → Устройства и завершите сессию
Deadline Assistant вручную. Невозможность связаться с Telegram не удерживает локальные права.

Для полного удаления откройте «Настройки → Аккаунт → Удалить мои данные», прочитайте предупреждение
и нажмите «Удалить все мои данные». Подтверждение одноразовое, привязано к владельцу и
действует 10 минут. Без подтверждения ничего не удаляется.

Удаляются профиль, зашифрованная сессия, чаты, события, источники, исправления, конфликты,
списки выбора, квитанции callback, журналы анализа, кеш результатов и доставки.
Активный анализ не сможет записать результат после удаления владельца.
Данные других пользователей сохраняются. Локальные права удаляются до попытки удалённого
отзыва. `/start` после удаления создаёт новый пустой профиль.

Удаление из БД — логическое удаление данных приложения, не гарантированное стирание
старых страниц SQLite, WAL, диска, журналов провайдера или резервных копий.
Администратор обязан применять политику хранения копий и учитывать условия LLM-провайдера.
Если нужна очистка носителя, выполняйте её штатными средствами хранения после остановки сервиса.

## 32. Частые ошибки и их решения

| Симптом | Что проверить |
| --- | --- |
| `check-config` вернул 3 | Перечисленные переменные, DATABASE_URL и `alembic upgrade head` |
| Ошибка конфигурации после ввода токена | HTTPS в PUBLIC_BASE_URL и корректный Fernet-ключ |
| HTTP 426 на странице | HTTPS-сертификат, reverse proxy, точный FORWARDED_ALLOW_IPS |
| HTTP 401 / ссылка истекла | Получите новую через /connect; старая ссылка одноразовая |
| Вход не начинается | Сравните заявку и подтвердите «Это я» в своём боте |
| Telegram требует 2FA | Пароль вводится только на HTTPS-странице |
| Telegram не прислал SMS | Проверьте Telegram-клиент: канал доставки определяет Telegram |
| Страница ожидает код в Telegram, но его нет | Проверьте служебный чат «Telegram» и архив; используйте повторный запрос после таймера, если он доступен, иначе новую ссылку и QR |
| Сессия отозвана | /connect заново; ключ шифрования должен быть прежним |
| Чат не виден | Членство и доступ истории у подключённого аккаунта, обновление каталога |
| LLM 401/403 | Ключ, права API и базовый URL, затем test-llm |
| LLM 404 / model not found | Точный идентификатор модели в каталоге своего провайдера |
| LLM 429 | Баланс, квоты, интервалы; снизьте LLM_CONCURRENCY и повторите позже |
| AnalysisValidationError | Ответ ИИ не прошёл проверку схемы или источников; точные коды ошибок есть в журнале без текстов переписки |
| InputTooLarge | Бюджет входа/выхода и контекст модели; большие пакеты дробятся, одно сообщение не режется |
| TimeoutError | Истекло время ожидания Telegram или ИИ; сохранённые порции не потеряны |
| AnalysisIdleTimeout | Нет прогресса дольше SYNC_TIMEOUT_SECONDS; следующий ночной запуск продолжит с checkpoint |
| JobBusy | Другой процесс уже обрабатывает пользователя; повторите после его завершения |
| Bot API conflict | Уже работает другой polling-процесс или установлен webhook |
| Бот ничего не присылает | /start в личном чате, блокировка бота, время и пояс профиля |
| Docker не запускается | Запущен ли Docker daemon; права на volumes; `docker compose logs app` |
| Unhealthy | Состояние БД, логи, завершённый polling; после исправления перезапустите app |
| После обновления старая конфигурация | В Compose пересоздайте контейнер, `restart` не обновляет env_file |

Не отправляйте в отчёт об ошибке `.env`, строку сессии, код, пароль или полные тексты чатов.
Обычно достаточно типа ошибки, версии приложения, времени и команды без секретных значений.

Команды разработчика:

```sh
uv run ruff check .
uv run ruff format --check .
uv run mypy src
uv run pytest -q
uv run python -m compileall -q src
uv run python scripts/verify_deployment.py --pytest-postgres
```

Обычные тесты используют временные БД и моки без настоящих платных запросов.
Проверка `verify_deployment.py` требует работающий Docker, собирает production-образ,
проверяет Compose с SQLite и PostgreSQL, затем удаляет только созданные ей тестовые
контейнеры и volumes. Она не читает рабочий `.env`. Три теста PostgreSQL пропускаются
в обычном pytest без `POSTGRES_TEST_URL`, но выполняются этой проверкой на временном сервере.
Проверяются полный пользовательский сценарий, CLI, dry-run, восстановление journal/checkpoint,
межпроцессная блокировка с SIGKILL, миграции SQLite и генерация SQL PostgreSQL, права владельца,
HTTPS/Origin/CSRF, версии сообщений, конфликты, расписание и очистка данных.
Opt-in проверка настоящего провайдера отдельно:
`RUN_LLM_INTEGRATION=1 uv run pytest -m integration -q` с `LOWROUTER_API_KEY` в окружении
и полными корректными настройками. Она делает реальные платные запросы; сама тестовая
команда не читает `.env` для ключа, пока вы не передадите окружение явно.

## 33. Вопросы безопасности

Секреты передаются через окружение или защищённый менеджер. Telethon StringSession
хранится только зашифрованной Fernet с привязкой к владельцу; файлов `.session` нет.
Номера, Telegram-коды, 2FA-пароли и phone_code_hash не сохраняются в БД и очищаются
из состояния завершённого входа. Ввод секретов разрешён только через HTTPS.

Каждый репозиторий ограничивает запросы user_id, внешние ключи препятствуют смешиванию
данных владельцев, SQL параметризован. Callback проверяет ID, владельца, срок и версию;
повторные действия фиксируются квитанциями. Подтверждение полного удаления проверяется
отдельно на сервере. Входящие команды и операции авторизации ограничены по частоте.

Веб-интерфейс не вставляет пользовательские строки как HTML. CSP запрещает посторонние
скрипты, встраивание страницы и сторонние соединения; действуют Origin/CSRF,
SameSite/HttpOnly/Secure cookies, no-store и no-referrer. На production включается HSTS.
Access log Uvicorn выключен. На reverse proxy также не записывайте тела авторизации.

LLM получает только выбранные сообщения и необходимую память событий/источников.
Сообщения, включая пользовательские исправления, маркируются как недоверенные данные:
содержимое чата не может менять системный протокол. У модели нет инструментов, доступа
к Telegram-аккаунту или SQL. Даже при prompt injection ответ проходит проверку операций,
ссылок, владельца и версий в Python. Это снижает риск, но не доказывает правильность смысла
дедлайна; спорные результаты проверяет человек.

По умолчанию завершённые и давно просроченные события удаляются через `RETENTION_DAYS=30`.
Будущая досдача, открытый конфликт, ожидающая правка и неизвестная дата защищены.
Ненужные тексты источников очищаются, пока общие источники актуальных событий сохраняются.
Минимальный хеш завершённого удалённого задания защищает от повторного создания;
при полном удалении аккаунта исчезает и он. Журналы, payload доставки и кеш LLM чистятся
по сроку хранения. Сырые обычные сообщения не журналируются.

JSON-логи выводятся в stdout, секретные поля маскируются, сторонние HTTP-логи отключены.
Формат содержит технические UUID, счётчики и типы ошибок, без полных сообщений и API-ключей.
Ограничьте доступ к логам, `.env`, БД и копиям. БД не открывается в интернет.
Платный API требует контроля расходов, а данные обрабатываются по условиям вашего провайдера.
