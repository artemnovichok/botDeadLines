# Отчёт о завершении разработки Deadline Assistant

Дата: 20 октября 2026 года, Europe/Moscow.
Проект продолжен на существующей реализации. Рабочие `.env` и `data/deadline.db`
не заменялись и не мигрировались; проверки использовали изолированные базы и синтетические данные.

## Реализованные возможности

- Добавлен Python CLI `python -m deadline_bot`: `run-cycle --all/--user`, `--send-now`,
  `--dry-run`, `send-summary`, `check-config`, `test-llm`, `serve`; для всех есть `--help`.
  Сообщения об ошибках и результатах на русском, коды завершения описаны в README.
- CLI, кнопки и ночной планировщик используют один `SyncService`; немедленная и утренняя
  отправка используют `SummaryDelivery`. После первого анализа бот присылает результат и сводку.
- Dry-run запускает тот же анализ в приватной временной копии данных одного владельца.
  Основная БД открывается для чтения, checkpoint и все постоянные таблицы сохраняются,
  отправка уведомлений исключена. Предложения выводятся в терминал.
- Реализованы межпроцессные блокировки пользователя, чата, пакета, сервера, доставки и
  Telethon-сессии: `flock` для SQLite, session advisory locks для PostgreSQL.
  Короткие SQLite-транзакции используют `BEGIN IMMEDIATE`, PostgreSQL — блокировки строк.
  Второй polling-сервер на ту же БД отклоняется, CLI может работать вместе с сервером.
- Валидированный ответ модели сохраняется до применения в `analysis_batches`.
  Повтор после сбоя между журналом и checkpoint повторно не вызывает LLM.
  События, источники, отметки обработки, статистика и checkpoint применяются атомарно.
- Добавлены ограниченная массовая обработка, общие между обычными процессами слоты LLM,
  интервалы запросов MTProto и Bot API, интервал на получателя, backoff и учёт FloodWait.
  Сетевые ошибки Telegram выделены в повторяемый тип, ошибки пользователей изолированы.
- Восстановление после рестарта не прерывает анализ живого CLI. Пропущенные ночные задачи
  догоняются; утренние доставки хранят payload и позицию успешно отправленной части.
- Сохраняются длительность, число новых/изменённых сообщений, событий, конфликтов,
  ошибок и usage. Полученные ответы LLM журналируются по числовому расходу, без содержимого.
  Стоимость не выдумывается и не рассчитывается без подтверждённого тарифа.
- Добавлено ограничение выхода модели. Слишком большие пакеты и ответы делятся без потери
  хвоста чата. Непомещающаяся единичная запись или память дают ошибку без обрезки данных.
- Команда `/delete_data` (`/delete_me`) требует подтверждения владельца с TTL 10 минут.
  Профиль и связанные данные удаляются каскадно, затем отзывается Telegram-сессия.
  Исправлен перехват этой кнопки общим callback-обработчиком меню.
- Сохранены HTTPS-only ввод Telegram-секретов, Origin/CSRF, Secure/HttpOnly/SameSite cookies,
  CSP и экранирование вывода, проверка владельца, версий и доказательств LLM-операций.
  Добавлены лимит входящих команд и запрет передачи ключа LLM по HTTP в production.
- Канонические имена настроек: `TELEGRAM_BOT_TOKEN`, `LOWROUTER_API_KEY`,
  `DAILY_SYNC_HOUR`, `DAILY_DIGEST_HOUR`. Прежние имена поддержаны для обновления установки.
- Alembic отделён от настройки бота/LLM; устранена зависимость миграций от HTTPS в `.env`.
  Миграция `0005_operations.py`, текущая ревизия `e105_operations`.
- Обновлены Dockerfile, `docker-compose.yml`, совместимый `compose.yaml`, PostgreSQL overlay,
  `.dockerignore`, entrypoint с поддержкой CLI-команд, healthcheck, volumes и рестарт.
  При неожиданном завершении polling сервер штатно завершается с кодом 5 для перезапуска.
- Созданы `scripts/backup_sqlite.py` и изолированная проверка
  `scripts/verify_deployment.py`; CI проверяет Python и контейнеры с обеими СУБД.
- README полностью переработан на русском, содержит все 33 запрошенных раздела,
  инструкции новичку, локальный/VPS запуск, HTTPS, обновление, backup/restore и ограничения.

## Проверенные сценарии

1. Настоящий aiogram Dispatcher с моками внешних API: `/start`, выдача и обмен ссылки,
   подтверждение владельца, ввод номера и кода через сервис веб-входа, сохранение шифрованной
   сессии, выбор учебного чата кнопками, первый анализ, получение дедлайна.
2. Новое противоречивое сообщение, создание конфликта без перезаписи даты, выбор варианта,
   обновление БД и сводка без нового LLM-вызова.
3. Ручной повторный анализ без дубликатов и нового списания за уже обработанные версии.
   Пропущенный ночной цикл после восстановления использует тот же checkpoint.
4. Сбой после сохранения ответа модели и до применения: checkpoint не сдвигается,
   повтор использует сохранённый ответ и создаёт событие ровно один раз.
5. Два независимых сервиса на одной БД одновременно запускают одного пользователя:
   модель вызывается один раз, итоговые события не дублируются.
6. Межпроцессная блокировка SQLite исключает другой настоящий процесс и освобождается
   после SIGKILL. Восстановление очереди не меняет статус живого CLI.
7. Ограничение параллельных LLM-запросов между независимыми клиентами.
   На PostgreSQL отдельно проверены advisory locks и атомарные бюджеты API.
8. Dry-run показывает предлагаемый дедлайн и оставляет побитно равными значения строк
   всех прикладных таблиц основной БД; отправки нет. Проверено и на PostgreSQL.
9. Деление большого контекста обрабатывает все сообщения до последнего без обрезки.
   Проверены также 1000 сообщений, редактирование старых источников и удалённый ID курсора.
10. CLI вызывает реальные внутренние сервисы при подменённых внешних API; send-summary
    не вызывает LLM, массовая ошибка возвращает 4 и сохраняет успех другого пользователя.
11. Собственные исправления, отмена правки, завершение, устаревшие/чужие callbacks,
    конфликты с 3+ вариантами и недоступные источники.
12. Очистка ненужных текстов с сохранением общих источников, будущей досдачи, неизвестной
    даты и открытых конфликтов. В середине ошибки очистка откатывается целиком.
13. Полное удаление требует своего действующего подтверждения; удаляются все связанные
    строки владельца, данные второго пользователя сохраняются.
14. HTTP/HTTPS, CSRF/Origin, одноразовые ссылки, подмена аккаунта, отзыв сессии и отсутствие
    секретов в ошибках веб-валидации.
15. Реальный локальный HTTP-процесс без внешних ключей: healthcheck, страница, SIGTERM.
    Отдельный процесс с упавшим мок-polling штатно завершает сервер с кодом 5.
16. SQLite backup API, защита от случайной перезаписи, права 600, восстановление старого
    содержимого поверх изменённой остановленной базы.
17. Собран production Docker-образ, запущены Compose-установки с пустой SQLite и PostgreSQL 17:
    миграции, `alembic check`, CLI, UID 10001, отсутствие `.env`/настоящих ключей в контейнере,
    healthcheck, рестарт, штатная остановка. Тестовые проекты и volumes удаляются после проверки.
18. Живой PostgreSQL: полный upgrade/check/downgrade/upgrade, read-only preview,
    параллельные циклы без дублей и общая координация. Для каждого теста создаётся отдельная БД.

## Известные ограничения

- Один polling-сервер/worker на установку. Сервер и несколько CLI координируются,
  горизонтальные polling-реплики и несколько Uvicorn workers не поддержаны.
- SQLite требует одного локального POSIX-диска; NFS и распределённая SQLite не поддерживаются.
  Для PostgreSQL session advisory locks нужен прямой доступ или session-pooling,
  PgBouncer transaction-pooling не подходит.
- Если процесс погиб между ответом провайдера и записью журнала, повторный платный вызов
  всё ещё возможен. Универсальной гарантии тарификации «ровно один раз» нет.
- Bot API не даёт idempotency key отправки. При падении между отправкой части сводки
  и фиксацией её прогресса возможно повторение этой части. Повторный ручной send-summary
  является новым явным запросом отправки.
- Неуспешная ручная отправка не подменяет ежедневную задачу: её можно повторить командой;
  автоматическое продолжение payload после рестарта относится к ежедневным доставкам.
- Dry-run обращается к настоящим Telegram/LLM при настоящих ключах и может быть платным.
  Он не прогревает основной кеш; слоты разных процессов dry-run изолированы от основной БД.
  При SIGKILL приватный временный каталог может остаться до очистки ОС.
- Не помещающаяся отдельно запись/память останавливает порцию до настройки бюджета;
  данные не обрезаются и checkpoint через неё не продвигается.
- Анализ текстовый; вложения, голосовые и опросы не распознаются. Семантическое качество
  и доступность модели проверяются пользователем на своих чатах.
- `/delete_data` удаляет данные приложения, но не гарантирует физическое стирание старых
  страниц диска, WAL, резервных копий и данных, уже переданных LLM-провайдеру.
- Запуск на публичном Linux VPS с конкретным DNS/сертификатом и реальная доставка Telegram
  в этой среде не выполнялись. Docker Desktop проверяет Linux-контейнеры на текущем хосте.

## Что необходимо настроить

- Не копировать `.env.example` поверх существующих секретов. Сверить настройки по README.
- TELEGRAM_BOT_TOKEN, TELEGRAM_API_ID, TELEGRAM_API_HASH, LOWROUTER_API_KEY,
  SESSION_ENCRYPTION_KEY, DATABASE_URL и точное имя доступной модели.
- Публичный HTTPS origin, сертификат, reverse proxy и FORWARDED_ALLOW_IPS.
  Read-only `check-config` текущего пользовательского `.env` обнаружил HTTP PUBLIC_BASE_URL
  при включённом боте. Для Python/VPS это нужно исправить; локальный Mac Docker-профиль
  сам задаёт `https://localhost:8443` в контейнере, не переписывая `.env`.
- Перед миграцией рабочей БД сделать резервную копию, остановить сервер/CLI,
  затем применить `alembic upgrade head`. Рабочая БД в ходе тестов не изменялась.
- Часовой пояс, время рассылки, бюджеты токенов/параллельности, ограничения расходов
  у провайдера, срок хранения копий. Для крупной истории увеличить общий таймаут и grace period.

## Что необходимо проверить вручную

- Настоящий BotFather-токен, отсутствие другого polling-процесса и старого webhook.
- HTTPS с действующим сертификатом из внешнего браузера; доверие только своему прокси.
- Реальное подключение того же Telegram по QR и с одного телефона, код и 2FA только на HTTPS.
- Чтение выбранных приватных групп и каналов, доступность истории и настоящих ссылок.
- `test-llm` с настоящим API-ключом, точное имя модели и качество понимания русской переписки.
- Утреннее уведомление в выбранном поясе, перенос срока, конфликт и собственная правка.
- Реальный отзыв сессии, удаление, повторное подключение; при неподтверждённом отзыве
  завершить сессию в Telegram → Устройства.
- Восстановление собственной зашифрованной копии на отдельной установке с прежним ключом.

## Команды для быстрого запуска

После заполнения настроек и HTTPS, из корня проекта:

```sh
uv sync --frozen
uv run python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
# Только при первой настройке перенесите результат в SESSION_ENCRYPTION_KEY.
uv run alembic upgrade head
uv run python -m deadline_bot check-config
uv run python -m deadline_bot test-llm
uv run python -m deadline_bot serve
```

Ручной цикл во втором терминале:

```sh
uv run python -m deadline_bot run-cycle --all --send-now
uv run python -m deadline_bot run-cycle --user 123456789 --send-now
uv run python -m deadline_bot run-cycle --all --dry-run
uv run python -m deadline_bot send-summary --user 123456789
```

VPS:

```sh
docker compose -f docker-compose.yml up -d --build
docker compose exec app python -m deadline_bot check-config
```

Изолированная проверка deployment без настоящих внешних ключей:

```sh
uv run python scripts/verify_deployment.py --pytest-postgres
```

Эта команда собирает образ, запускает временные Compose-проекты и удаляет только их
контейнеры/volumes. Пользовательский `.env` и рабочие данные не используются.

## Запуск на своём Mac двойным щелчком

`start.command` и `stop.command` переключены на отдельный `compose.macos.yaml`.
Покупка сервера и домена не требуется. Скрипт запускает Docker Desktop, собирает образ,
готовит 90-дневный серверный TLS-сертификат localhost (не CA), добавляет ограниченное
SSL/localhost-доверие в пользовательскую связку ключей с системным подтверждением при
необходимости, создаёт копию существующей `data/deadline.db`, применяет миграции и запускает
контейнер. `.env` с ключами сохраняется; только адрес, пути TLS и локальной БД переопределены
в контейнере. Абсолютный путь БД одинаков на хосте и в контейнере для общих SQLite-блокировок.
Контейнер работает под UID/GID пользователя Mac, порт опубликован только на 127.0.0.1:8443.

После старта ссылку подключения из Telegram нужно открывать **на этом же Mac**.
`stop.command` останавливает только контейнер этого проекта по Compose labels.
Закрытие Terminal и Ctrl+C завершают показ журналов; контейнер останавливается отдельным stop.

Проверены тестовый Docker-профиль с временной SQLite без пользовательских ключей,
подтверждённый HTTPS через SSLContext с точным сертификатом, /connect, миграции,
непривилегированный UID, файлы на хосте и штатная остановка. macOS проверил сертификат
через verify-cert с явным временным trust anchor. Связка ключей при тестах не изменялась;
её изменение и настоящий запуск пользователь выполняет сам при первом start.
