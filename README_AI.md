# Deadline Assistant: вводная для следующего AI-агента

Снимок контекста: **25 октября 2026, Europe/Moscow**. Этот файл помогает продолжить
работу по исходникам без доступа к прошлому чату. Реальный статус процессов, содержимое
окружения и доступность внешних сервисов нужно проверять на конкретной установке.

## 1. Зачем создан проект

Это многопользовательский Telegram-помощник по учебным дедлайнам. Задания и переносы
разбросаны по группам и каналам; студенту нужна одна актуальная картина с источниками,
условиями сдачи и напоминаниями. Бот собирает доступный текст выбранных чатов через
подключённый аккаунт пользователя, извлекает учебные события с помощью LLM и присылает
сводку. У каждого пользователя свои чаты, события, Telegram-сессия, часовой пояс,
время сводки и учебная группа.

Бот-токен используется для интерфейса и доставки сообщений. Историю выбранных чатов
читает Telethon от имени явно подключённого пользователем аккаунта. Добавление бота
в группы не заменяет это подключение.

## 2. Что уже реализовано

- Вход в Telegram через одноразовую HTTPS-страницу: QR, телефон, код и 2FA;
  проверка, что аккаунт принадлежит владельцу диалога с ботом; шифрование сессий Fernet.
- Выбор чатов; первичный анализ до 1000 сообщений на чат с окном по умолчанию 90 дней;
  последующие запуски обрабатывают новые сообщения и изменения известных источников.
- Дедлайны, экзамены, встречи, переносы, отмены, условия досдачи и штрафы;
  источники событий, конфликты, пользовательские правки, отмена правки и завершение.
- Постоянная учебная группа пользователя и её передача в контекст анализа.
- Ночной анализ и утренняя сводка; по умолчанию 02:00 и 08:00 в поясе пользователя.
- Фоновые задания, прогресс, `/status`, `/stop_sync`, продолжение с checkpoint,
  мягкие пределы времени/токенов и частичный результат `partial`.
- CLI для того же анализа, отправки сводок, проверки конфигурации и запуска сервера.
- SQLite или PostgreSQL, миграции, межпроцессная координация, резервная копия SQLite,
  Docker/VPS и отдельный локальный профиль macOS с HTTPS.

Это существующая реализация, а не заготовка. Начинайте с поиска нужного сервиса и тестов.
Реальное качество извлечения фактов зависит от модели; наличие тестов не доказывает
безошибочное понимание любых учебных переписок.

## 3. Стек и карта проекта

APScheduler 3, Pydantic 2, OpenAI SDK для совместимого API. Провайдер по умолчанию
задан в конфигурации как LowRouter; имя модели и URL настраиваются.

## 4. Путь данных и инварианты

```text
Telegram-профиль → выбранные чаты → сообщения и версии источников
  → SyncService → пакеты LLM → проверка операций Python
  → транзакция: события + источники + обработанные версии + checkpoint
  → конфликты / сводка из БД → Bot API
```

Сохраняйте эти свойства при изменениях:

1. **Изоляция владельцев.** Проверяйте пользователя, чат, источник, событие и callback;
   знание ID само по себе не даёт доступа к чужим данным.
2. **Общий анализ.** Бот, ночное расписание и CLI идут через существующие SyncService
   и CycleService. Не создавайте независимую вторую реализацию.
3. **Контроль модели.** Модель предлагает типизированные операции; Python проверяет
   схему, принадлежность, версии и ссылки на переданные источники. Модель не исполняет
   SQL и не получает сессию Telegram.
4. **Сохранность прогресса.** Ответ сохраняется в `analysis_batches` до применения;
   применение и checkpoint фиксируются атомарно. Не продвигайте курсор через
   необработанные сообщения и не обрезайте молча текст ради бюджета.
5. **Повторяемость.** Повтор уже обработанной версии и восстановление сохранённого
   пакета не должны создавать дубли или повторно вызывать LLM без причины.
6. **Конфликты и правки.** Не заменяйте спорную дату догадкой и не затирайте ручные
   исправления без предусмотренной доменной операции. Недоступный источник не означает отмену события.
7. **Время.** Хранение и доменные сравнения используют UTC; ввод и сводка учитывают
   пояс пользователя. Относительные даты относятся к времени исходного сообщения.
8. **Расходы.** `SYNC_TIMEOUT_SECONDS` ограничивает отсутствие прогресса;
   `SYNC_MAX_DURATION_SECONDS` и `SYNC_MAX_TOTAL_TOKENS` проверяются между порциями.
   Не превращайте их в бесконтрольные перезапуски оплачиваемых запросов.

## 5. Быстрый запуск новой установки

Полная инструкция с ключами, HTTPS и Docker — в [README.md](README.md).

```sh
uv sync --frozen
# Только для НОВОЙ установки; существующий .env не перезаписывать:
cp .env.example .env
chmod 600 .env
```

Заполните `TELEGRAM_BOT_TOKEN`, `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`,
`LOWROUTER_API_KEY`, `SESSION_ENCRYPTION_KEY`; проверьте `DATABASE_URL`,
`PUBLIC_BASE_URL` и доступное у вашего провайдера имя `LLM_MODEL`.
Ключ Fernet генерируется один раз и хранится отдельно от БД. Его замена лишит
доступа к существующим зашифрованным сессиям.

Для прямого Python-запуска настройте действующий HTTPS origin и TLS или reverse proxy,
затем выполните:

```sh
uv run alembic upgrade head
uv run python -m deadline_bot check-config
uv run python -m deadline_bot serve
```

На Mac с Docker Desktop используйте `start.command` и `stop.command`
(или `python3 scripts/macos_docker.py --help`). Локальный профиль
`compose.macos.yaml` задаёт `https://localhost:8443`, создаёт TLS и использует
существующий `data/deadline.db`. Ссылку подключения нужно открывать на том же Mac.
Скрипт может запросить системное подтверждение доверия локальному сертификату.
Имя Compose-проекта зависит от абсолютного пути каталога: при перемещении проекта
проверьте старый контейнер, чтобы случайно не запустить второй polling-сервер.

`compose.yaml` / `docker-compose.yml` — обычный Docker-профиль;
`compose.postgres.yaml` — дополнение PostgreSQL. У обычного профиля данные находятся
в Docker volume, у Mac-профиля — в локальном `data/`; это разные места хранения.
Не переносите установку между ними без явного переноса данных и ключа.

## 6. Команды эксплуатации

```sh
uv run python -m deadline_bot --help
uv run python -m deadline_bot check-config
uv run python -m deadline_bot run-cycle --user 123456789
uv run python -m deadline_bot run-cycle --all --send-now
uv run python -m deadline_bot run-cycle --all --dry-run
uv run python -m deadline_bot send-summary --user 123456789
```

ID выше — пример. `run-cycle` может обращаться к настоящим Telegram и LLM;
`--send-now` также отправляет сообщения. `--dry-run` не меняет основную БД
и не отправляет сводку, но реальные API-вызовы и расходы возможны.
`send-summary` берёт данные из БД без LLM и отправляет сообщение.
`test-llm` делает настоящий, потенциально платный запрос.

Коды CLI: `0` — успех, `2` — аргументы/пользователь, `3` — конфигурация,
`4` — частичный результат или ошибки отдельных пользователей, `5` — сбой выполнения.
`check-config` проверяет конфигурацию и версию схемы без внешних запросов,
но не доказывает работоспособность ключей и доступность модели.

## 7. Проверки перед загрузкой изменений

```sh
uv sync --frozen
uv run ruff check .
uv run ruff format --check .
uv run mypy src
uv run pytest -q -m 'not integration and not postgres'
uv run python -m compileall -q src
uv lock --check --offline
```

Обычные тесты используют временные БД и моки. Маркеры `integration` и `postgres`
явно исключены в приведённой команде. Три LLM-теста требуют opt-in
`RUN_LLM_INTEGRATION=1` и ключ в окружении; три PostgreSQL-теста требуют
`POSTGRES_TEST_URL` и создают/удаляют собственные тестовые БД.
Дополнительная проверка Docker и PostgreSQL без рабочих ключей:

```sh
uv run python scripts/verify_deployment.py --pytest-postgres
```

Для неё нужен работающий Docker daemon. Исторические результаты находятся в
[docs/verification.md](docs/verification.md) и [DEVELOPMENT_REPORT.md](DEVELOPMENT_REPORT.md).
Не выдавайте их за собственный актуальный запуск.

При подготовке репозитория 25 октября 2026: **313 passed, 6 deselected**;
Ruff, форматирование, strict mypy, compileall и проверка lockfile прошли.
Docker, PostgreSQL и реальные внешние API в этой проверке не запускались.

## 8. Данные, миграции и ограничения

- В репозиторий входят исходники, тесты, миграции, документация, конфигурационные
  шаблоны, lockfile и CI. `.env`, `data/`, БД/WAL, Telegram-сессии, ключи TLS,
  логи, кеши, `.venv`, `dist/` и локальные результаты анализа исключены.
- Рабочая БД содержит приватные тексты и сессии. Перед её миграцией или переносом
  сделайте согласованную копию через `scripts/backup_sqlite.py`, сверившись с его `--help`;
  миграции рабочей установки выполняйте без конкурирующих серверных/CLI изменений.
- Изменение схемы требует новой Alembic-миграции и обновления
  `src/deadline_assistant/db/schema.py:SCHEMA_REVISION`.
- Поддерживается **один polling-сервер на БД**. Не используйте несколько Uvicorn
  workers и горизонтальные polling-реплики. Обычные CLI координируются с сервером.
- SQLite требует общего локального POSIX-диска и файловых блокировок, не NFS.
  Для PostgreSQL нужны session advisory locks: прямое соединение или session pooling;
  PgBouncer в transaction pooling не подходит.
- Анализируется текст; вложения, фотографии, голосовые и опросы не распознаются.
- Между ответом LLM и записью журнала остаётся окно возможного повторного платного
  запроса. Между отправкой сводки и сохранением прогресса возможно повторение её части.
- Удаление данных приложения не стирает автоматически резервные копии и данные,
  уже переданные внешнему провайдеру.

## 9. С чего продолжать работу

Сначала уточните текущую задачу по запросу владельца и проверьте состояние Git.
Прочитайте затрагиваемые сервисы и их тесты, затем вносите локальное изменение.
При проблемах запуска сначала проверяйте профиль Docker, наличие единственного
polling-процесса, HTTPS, версию схемы и безопасные журналы; не публикуйте секреты.
Старые отчёты содержат разные числа тестов и результаты прошлых экспериментов с моделями;
источник текущего поведения — код, актуальная конфигурация и воспроизводимая проверка.
