# Анализ переписки через LowRouter

Настройки по умолчанию: `LLM_BASE_URL=https://api.lowrouter.ru/v1`,
`LLM_MODEL=gpt-6-luna`, `LLM_TIMEOUT_SECONDS=120`, `LLM_MAX_RETRIES=3`,
`LLM_MAX_INPUT_TOKENS=30000`. Ключ задаётся через `LOWROUTER_API_KEY`.
`LLM_MAX_RETRIES` применяется только к явным отказам 429. Автоповторы SDK отключены:
таймаут, обрыв связи или HTTP 5xx не запускают ту же генерацию снова, поскольку
шлюз мог продолжить и оплатить первоначальную обработку. Ограниченные исправления
невалидного формата остаются отдельным механизмом `LLM_FORMAT_RETRIES`.

Используется только OpenAI-compatible Chat Completions, без tools, веб-поиска,
SQL, выполнения кода и дополнительных услуг провайдера. Все сообщения, включая
пользовательские исправления, являются данными внутри JSON. Динамические данные
никогда не подставляются в системные инструкции.

## Вход и формат ответа

Python передаёт текущую местную дату и время, IANA-пояс, сообщения с ID чата и сообщения,
названием чата, автором и известной ролью, исходной датой, edit_timestamp и reply_to.
В `user_profile` передаются сохранённая учебная группа и её числовой номер.
Например, `БПИ267` соответствует `267`: модель выбирает пятницу в 9:30 из
распределения «четверг — 262, 264, 265, 268, 2610; пятница — 261, 263, 266, 267, 269».
Если группа не задана или распределение неоднозначно, требуется уточнение.
Профиль передаётся только как JSON-данные. Смена группы во время анализа отклоняет
устаревший результат; группа также входит в ключ кеша пакетов.
Каждое сообщение отмечено как `untrusted_telegram_message`. Относительные сроки считаются
от даты сообщения. Неизвестная роль не превращается в роль преподавателя.

`memory` собирается из SQL и содержит UUID/версии актуальных событий, сохранённые
версии источников и исправления с хронологией. Поля событий без изменений от значений
по умолчанию опущены; общие `event_defaults` передаются один раз. Основной дедлайн,
период досдачи и подтверждённое завершение определяют актуальность. Старые события
подключаются при связи нового текста с предметом/названием или reply/ID источника.
Неразрешённые конфликты и исправления сохраняются в контексте до решения.
Каталог актуальных EventData остаётся общим для сопоставления между чатами,
но полные источники загружаются только для событий текущего чата, связанных
по предмету/названию/ссылке сообщений, исправлений и конфликтов. Неиспользованные
тексты не удаляются из БД и доступны через меню источников. Отсутствие полного
источника в текущем контексте не означает отмену или отсутствие события.

Ответ — `{"operations": [...]}`. Допустимы:

| op | Содержимое |
| --- | --- |
| create_event | Полное EventData и evidence; UUID назначает сервер |
| update_event | UUID, expected_version, EventData, evidence, reason |
| cancel_event / complete_event | UUID, expected_version, evidence, reason |
| add_source | UUID, expected_version, evidence, reason |
| create_conflict | UUID, expected_version, reason, evidence и 2–10 состояний с отдельными evidence |
| no_action | reason |

`evidence.messages` содержит пары `{chat_id, message_id}` из новых сообщений;
`source_ids` содержит UUID сохранённых версий; `correction_ids` — UUID исправлений.
Сообщения с одинаковыми ID в разных чатах различаются. Свидетельства не могут ссылаться
на другого пользователя или другое исправляемое событие. Изменение требует нового
подтверждения; для явной повторной проверки можно использовать сохранённые источники.

EventData хранит название, предмет, описание, тип, статус, обязательность, уверенность,
место, основной срок и его точность, конец интервала, условия, штрафы и период досдачи.
`expected_release` означает ожидание выдачи, а не дедлайн сдачи. Продление без даты
требует уточнения, а не вычисления вымышленного срока. Один период досдачи хранится
в том же событии. Схемы находятся в `src/deadline_assistant/domain.py`.

Сначала адаптер запрашивает строгую JSON Schema. Явная ошибка неподдерживаемого
response_format переключает его на JSON object, затем text. Прочие ошибки 400,
авторизации и доступа не маскируются fallback. Ответ всегда валидируется Pydantic
и проверкой ссылок. Допускается `LLM_FORMAT_RETRIES=2` исправления формата/ссылок;
невалидный ответ никогда не применяется частично.

Схема также включена непосредственно в системные инструкции: совместимый шлюз может
принять `response_format`, но не применить ограничение к генерации. Для лабораторных
используется `event_type=lab`, название `event.title` обязательно, `create_event`
не принимает `event_id`. Повторная попытка получает конкретные ошибки полей или ссылок.
В журнал попадают только коды проверки, известные схеме имена полей и безопасные
сообщения приложения; ответы модели, переписка и неизвестные имена полей не записываются.
После исчерпания попыток статус содержит понятную причину `AnalysisValidationError`.

## Транзакции, память и checkpoint

Первый анализ читает до 1000 последних доступных сообщений на чат.
В ИИ передаются сообщения за последние `MESSAGE_MAX_AGE_DAYS=90` дней
(по дате отправки или более свежего редактирования). Старые сообщения отмечаются
обработанными без вызова ИИ; checkpoint продвигается и в полностью старом чате.
Прямые проверки уже известных источников не ограничены этим окном.
Новые события с полностью прошедшим сроком и досдачей не записываются, даже если
модель выставила `needs_clarification`. Сохранённая прошедшая дата с этой пометкой
также не удерживается в сводке или несвязанной памяти; события без даты, действующая
досдача и неразрешённые конфликты сохраняются. Год старого объявления не подменяется. Последующие чтения
используют `min_id=checkpoint`, независимо от существования самого сообщения-курсора.
Переписка обрабатывается по возрастанию ID. Каждая порция получает свежую память из SQL.
Превышение входного бюджета делит порцию пополам; каждая половина фиксируется отдельно.
Непомещающиеся единичное сообщение или память приводят к явной ошибке без обрезки данных.

`SYNC_TIMEOUT_SECONDS=600` — предел отсутствия прогресса. После commit каждой порции,
включая рекурсивное деление и обновление источников, срок ожидания продлевается.
Отсчёт обновляется также после проверки чата и обработки очередного исправления.
Длительность истории больше не ограничена таймаутом бездействия, пока есть прогресс.
Если порция зависла, `AnalysisIdleTimeout` останавливает её; прежние commit, checkpoint
и journal остаются. Внешние запросы сохраняют собственные таймауты и лимиты повторов.
`/status` во время работы показывает текущее прошедшее время и сохранённые счётчики.
Каждые `ANALYSIS_PROGRESS_INTERVAL_SECONDS=120` секунд бот сообщает прогресс
без запроса к ИИ. `/stop_sync` отменяет фоновую задачу текущего пользователя;
сохранённые порции остаются, незавершённый запрос мог быть уже оплачен.

Для одного запуска действуют мягкие пределы `SYNC_MAX_DURATION_SECONDS=300` и
`SYNC_MAX_TOTAL_TOKENS=100000`. Время проверяется после сохранения порции/фазы,
токены по usage провайдера — перед следующей порцией истории. Текущая порция
досохраняется и может превысить эти значения, как и её ограниченные попытки.
При достижении предела AnalysisRun получает `partial` без ошибки; бот отправляет
статус и текущую сводку с предупреждением. Повторный `/sync` продолжит историю.
CLI отображает частичный результат и возвращает код 4. Даже при ошибке после
сохранённых порций бот отправляет текущую сводку с предупреждением. Это ограничение объёма
обработки, не точная гарантия расходов у стороннего провайдера.

Для известных GPT-моделей размер входа считается `tiktoken` с кодировкой модели,
а не по числу байтов UTF-8. Учитываются инструкции, схема, полная память, сообщения,
ошибки повторной проверки и запас на служебный формат. Для неизвестных токенизатору
моделей сохраняется верхняя оценка по UTF-8. GPT-6 и шлюзовые имена
`gpt-6-luna`, `gpt6-luna`, `openai/gpt-6-luna` при старой версии tiktoken
используют оценку BPE `o200k_base`, сохраняя исходное имя модели в API-запросе.
Это оценка семейства GPT, а не подтверждённый точный токенизатор шлюза.
`LLM_TOKEN_ENCODING` позволяет явно выбрать кодировку. Локальный подсчёт
не заменяет проверку лимита провайдером. Диагностика размера содержит только
числа и название кодировки; ошибки входного и выходного бюджета различаются.
В соответствии с [API OpenAI](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)
`max_completion_tokens` включает видимый ответ и токены рассуждений. Схема `response_format` учитывается
дополнительно только в режиме `json_schema`. Словари токенизатора загружены в Docker-образ
при сборке; работающий контейнер не скачивает их и поддерживает `read_only`.

`LLM_REASONING_EFFORT` позволяет явно настроить рассуждения. Для GPT-6 по умолчанию
передаётся `low`, для остальных моделей параметр опущен. Значения сверены с
[OpenAI Docs для GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna).
Явный ответ шлюза о неподдерживаемом `reasoning_effort` отключает этот параметр
один раз; неизвестные ошибки не маскируются. Скорость и семантическое качество
зависят от шлюза: в платной проверке LowRouter возвращал токены рассуждений
даже с `none`. Одно принятие параметра не доказывает, что шлюз его применяет.

`LLM_STREAM=true` включает SSE с `stream_options.include_usage`. Адаптер собирает
только содержимое ответа, учитывает завершающий блок расхода и проверяет JSON
после окончания потока. Токены рассуждений не попадают в JSON. Незавершённый
или обрезанный поток не применяется и автоматически не повторяется.
По умолчанию streaming выключен для совместимости со сторонними шлюзами.
`LLM_TIMEOUT_SECONDS` ограничивает весь один сетевой запрос, включая чтение
потока; keepalive-пакеты не продлевают этот предел. В живой проверке GPT-6 Luna первый ответ приходил позже 120 секунд;
проверялась конфигурация SSE с ожиданием 300 секунд. Streaming сам по себе
не уменьшает время генерации и не гарантирует ответ раньше тайм-аута.

При `created: null` в SSE служебная метка времени не заменяет сохранённое значение.
Это наблюдалось у Claude через LowRouter; даты учебных событий не затрагиваются.
Единственный полный JSON-блок Markdown разбирается локально без платного исправления.
Окружающий текст не отбрасывается, схема и проверка доказательств остаются обязательными.
Текстовая ошибка шлюза `[Error] ... upstream provider ...` прерывает анализ как
`LLMProviderUnavailable`, а не запускает повторные запросы для исправления формата.

Сетевые вызовы выполняются вне транзакции. Перед применением Python снова проверяет
владельца, подключение, UUID и версии. Операции, источники, processed_messages, статистика
и checkpoint фиксируются вместе. Ошибка откатывает порцию; предыдущие успешные порции
сохраняются. Повторный запуск пропускает уже применённые версии. Пустой валидный результат
тоже отмечает порцию обработанной. Параллельная ручная правка делает результат устаревшим.

Сырой чат живёт только в памяти. В БД сохраняются тексты доказательств и исправлений;
бесконечный JSON-контекст не ведётся. Каждый цикл запрашивает исходные ID активных событий
и конфликтов напрямую, в том числе вне окна последних сообщений. Сравниваются текст
и edit_timestamp. Исчезновение источника меняет available, сохраняя его текст и событие.
Тексты источников открытых и неподтверждённых конфликтов защищены от retention.

## Исправления и конфликты

Меню «Редактировать дедлайн» сопоставляет временные номера с UUID в FSM. Текст исправления
сохраняется до вызова модели. Успешная операция применяется сразу. При сетевой ошибке
исправление остаётся pending; синхронизация повторяет такие исправления даже без новых
сообщений. Последнее применённое исправление передаётся в будущие запросы с датой создания.

Новые события с уверенностью < 0.65 получают пометку «Требует уточнения».
Однозначные изменения с уверенностью >= 0.65 применяются сразу. Спорные и менее уверенные
изменения создают конфликт. Полные варианты EventData, UUID источников, тексты и привязки
исправлений сохранены заранее. Совпадающие варианты сливаются; разные могут добавляться.
Текущее состояние включается автоматически. Версия события фиксируется в конфликте
и callback. После любого более свежего изменения старый выбор отклоняется.
Конфликты из прежней схемы, где версии не было, миграция помечает устаревшими;
перед выбором их необходимо повторно проверить.

Кнопка «Вариант N» проверяет владельца и версию, атомарно применяет подготовленное состояние,
закрывает конфликт и отправляет сводку без LLM. «Оставить неподтверждённым» сохраняет варианты
и пометку уточнения. Если варианты устарели, «Проверить снова» запускает новый анализ памяти.
Перед утренней сводкой отправляются карточки конфликтов; они не блокируют остальные события.

## Проверки

`uv run pytest -q` использует моки Telegram и LLM. Русские сценарии находятся в
`tests/fixtures/russian_cases.json` и тестах: 1000 сообщений с поздравлениями, КР, перенос,
досдача, необязательность, слух против сообщения преподавателя, правка пользователя,
удаление и редактирование источника, удалённый курсор, следующий месяц и год.
Проверяются схема, ссылки, операции, владение, дубли, повторные запуски, откат,
порции, конфликты 3+, кнопки без LLM, устаревшие версии и утренняя доставка.

Семантическое понимание проверяется реальной моделью только по явному включению:

```sh
RUN_LLM_INTEGRATION=1 uv run pytest -m integration -q
```

LOWROUTER_API_KEY должен быть экспортирован в окружение; `.env` сам по себе не включает integration-test.
Это платные вызовы. Доступность LowRouter, конкретной модели и Telegram-аккаунта моками
не подтверждается. Для запуска после обновления выполните `uv run alembic upgrade head`.

## CLI, журнал и межпроцессные запуски

`python -m deadline_bot run-cycle --all --send-now` вызывает тот же SyncService,
что ночной планировщик и кнопка анализа. `send-summary` обращается только к БД.
Dry-run копирует данные выбранного владельца в приватную временную SQLite и выполняет
этот же сервис там; основная БД открыта для чтения, уведомлений нет.

Пользователь и пакет защищены межпроцессными блокировками. До применения сохраняется
валидированный ответ в analysis_batches; хеш учитывает схему, модель, провайдера,
сообщения и контекст. Повтор после сохранения журнала не вызывает API заново.
Если процесс погиб до записи ответа, универсальной гарантии отсутствия повторной оплаты нет.
Кеш удаляется по RETENTION_DAYS и каскадно при удалении аккаунта.

LLM_CONCURRENCY ограничивает обычные запросы между процессами одной установки.
Dry-run использует собственные временные данные и общий semaphore внутри текущего CLI;
отдельные процессы dry-run не делят основной бюджет. Ответ ограничен LLM_MAX_OUTPUT_TOKENS;
превышение контекста или обрезанный ответ приводят к делению пакета, без обрезки текста.
Расход каждого полученного ответа журналируется числами, без содержимого переписки.
