# Подключение Telegram: протокол и проверка

Второй этап расширяет существующие модели и сервисы. Перед обновлением остановите процесс,
сохраните резервную копию БД и выполните `uv run alembic upgrade head`. Миграция
`b821_connection` добавляет поля подтверждения, попыток, статистики и верхней границы истории.
Существующие дедлайны, источники и зашифрованные Telegram-сессии сохраняются. Старые
незавершённые ссылки подключения инвалидируются.

## Реальный вход

Используются документированные методы [Telethon 1](https://docs.telethon.dev/en/stable/modules/client.html):
`qr_login().wait()`, `send_code_request`, `auth.ResendCodeRequest`, `sign_in` и `log_out`.
Telegram Login Widget не предоставляет пользовательскую MTProto-сессию и здесь не используется.

QR подтверждается в официальном приложении Telegram на другом устройстве. Вход с одного
телефона требует переключения между HTTPS-страницей сервиса и каналом доставки кода,
который выбрал Telegram. Автоматического входа по deep link на том же телефоне нет.
После `SessionPasswordNeededError` пароль передаётся исключительно в `sign_in(password=...)`.
Приложение не создаёт новые Telegram-аккаунты и не обходит ограничения выдачи кодов.

Поддерживаются коды в Telegram, SMS, звонок и код на настроенную почту, если Telegram
предоставил соответствующий `SentCodeType`. SMS нельзя гарантировать или принудительно
включить. Необычные варианты, требующие настройки почты, оплаты, Firebase или других
неподдерживаемых шагов, закрывают вход с понятным предложением использовать QR или
повторить позже. Неподдерживаемый способ не имитируется.

При `SentCodeTypeApp` код нужно искать в служебном чате «Telegram» на уже подключённых
устройствах, включая архив. Ответ API сообщает выбранный способ, но не подтверждает,
что пользователь фактически получил сообщение; работа QR не доказывает доставку кода.
Если Telegram вернул `next_type` SMS/звонок, страница показывает кнопку повторного запроса,
доступную после `timeout`. Сервер самостоятельно проверяет таймер и общий лимит попыток, вызывает
`auth.resendCode` с текущим `phone_code_hash` и сохраняет новый hash из ответа.
Повторного запроса без нажатия кнопки нет. Если поддерживаемого следующего способа нет,
страница предлагает отменить вход и получить новую ссылку для QR со второго устройства.
Подробности протокола: [User Authorization](https://core.telegram.org/api/auth) и
[auth.resendCode](https://core.telegram.org/method/auth.resendCode).

## Привязка и состояния

1. Handler из личного чата получает владельца из проверенного Bot API update. Группы,
   каналы и callback без личного сообщения этого же пользователя не обрабатываются.
2. Сервер создаёт 32 случайных байта через `secrets.token_urlsafe(32)`. В БД хранится SHA-256
   токена, срок — 10 минут. Новая ссылка инвалидирует предыдущую.
3. Фрагмент `/connect#token=...` не отправляется веб-серверу. JavaScript сразу удаляет
   его из адресной строки, затем выполняет одноразовый POST exchange. Секреты Telegram
   никогда не передаются в URL.
4. Exchange атомарно потребляет токен и устанавливает HttpOnly/Secure/SameSite=Strict
   браузерную cookie. CSRF-токен связан с этой сессией и передаётся заголовком.
5. Владелец сравнивает номер заявки в браузере и боте, нажимает «Это я». Callback сверяет
   владельца с БД. Украденная ссылка не позволяет начать вход без этого подтверждения.
6. Перед сохранением `get_me().id` обязан совпасть с Telegram ID инициатора. Чужой аккаунт
   отзывается через `log_out`; его сессия не сохраняется ни одному пользователю.
7. Сессия шифруется Fernet с ключом из `SESSION_ENCRYPTION_KEY` и привязкой к внутреннему UUID.
   После commit бот отправляет уведомление. При переподключении сервис пытается отозвать
   предыдущую сессию; Telegram → Устройства позволяет проверить и завершить её вручную.

Состояния: `approval_required → idle → waiting` (QR) или `code_required` (телефон), затем
при необходимости `password_required → connected`. Ошибки заканчиваются `wrong_account`,
`expired` или `failed`. Отмена удаляет ссылку, инвалидирует браузерную cookie и закрывает
незавершённый Telethon-клиент. Повторное использование и обмен одной ссылки двумя
браузерами запрещены. Отмена завершённой заявки не является отключением сохранённого
аккаунта; для этого есть отдельная команда и кнопка.

POST требует точного Origin и, после exchange, CSRF. Ограничения: 5 выдач ссылки за 10 минут
на владельца, 20 обменов в минуту на IP / 300 глобально, 5 операций с секретами на ссылку
(включая первый и повторные запросы кода). Счётчик последних хранится в БД.
Попытка повторного запроса до истечения таймера не расходует этот лимит.
Сетевые ошибки и FloodWait не приводят к удалению дедлайнов.
`Retry-After` выдаётся при ограничении частоты.

Номера, коды, пароли и `phone_code_hash` живут только в памяти незавершённого входа.
Полей для них в БД нет; пароли не сохраняются в PendingLogin. В браузере нет аналитики,
сторонних скриптов и хранилищ localStorage/sessionStorage. Ответы и HTML не кэшируются.
Ошибки валидации и интеграций не отражают введённые секреты или чужие сообщения ошибок.
Логи внешних библиотек и access log отключены.
Для диагностики входа журнал содержит только имя типа доставки, имя следующего типа,
таймер и класс RPC/сетевой ошибки; ответ Telegram целиком и текст исключения не пишутся.

## HTTPS и перезапуск

Установите `PUBLIC_BASE_URL=https://ваш-домен`, настройте действующий TLS-сертификат и
reverse proxy. `FORWARDED_ALLOW_IPS` содержит только адреса вашего прокси; Uvicorn использует
его для доверия `X-Forwarded-Proto`. Для Docker укажите адрес, с которого прокси виден
контейнеру. Порт приложения доступен только локально. Для HTTP секретные endpoints отвечают
426, а клиентская страница вообще не отправляет введённые данные. HTTP localhost пригоден
для health checks и просмотра внешнего вида. Запуск с `TELEGRAM_BOT_TOKEN` требует HTTPS origin.

После рестарта сохранённая сессия расшифровывается при следующем обращении к Telegram.
Код входа повторно не нужен, если Telegram не отозвал сессию. Незавершённые входы хранятся
в памяти: обновите страницу и начните заново в пределах срока ссылки. При отзыве сессии
статус меняется на `revoked`, бот один раз предлагает переподключение. Старые дедлайны
и выбор чатов сохраняются. Явное отключение удаляет сессию и выключает чаты.

Для PostgreSQL короткие транзакции одного пользователя сериализуются блокировкой строки
владельца. После сетевого анализа снова проверяются текущая сессия и enabled чата, поэтому
поздний результат не сохраняется после отключения. Сетевые вызовы не держат блокировку БД.
Для polling, авторизации и FSM работает один серверный процесс/worker. Его защищает
межпроцессная блокировка сервера. Одновременные CLI координируют анализ и Telethon-сессии
через flock (SQLite на одном локальном диске) либо PostgreSQL session advisory locks.
Общие бюджеты API хранятся в БД; очередь и сведения о результатах анализа восстанавливаются
без прерывания живого CLI. Несколько polling-реплик не поддерживаются.

## Чаты и первый анализ

После авторизации обязательна учебная группа. Рабочее меню, выбор чатов и настройки
расписания доступны только при подключённом аккаунте и сохранённой группе.

Список диалогов запрашивается без ограничения первыми 200. FSM хранит черновик выбора;
сохранение повторно проверяет доступ через текущую сессию. Бот показывает 8 чатов на страницу,
ищет по части названия и сохраняет многократный выбор. Недоступный ранее выбранный чат можно
снять. Сохранение пустого выбора отключает все чаты только этого пользователя.

Идентификатор — стабильный marked Telegram ID. Метаданные включают тип peer, числовой ID,
access hash и необязательный username. Приватные группы поддерживаются без username.
Ссылки формируются из настоящего PeerChannel: публичные `t.me/username/message_id`,
приватные `t.me/c/channel_id/message_id`. Для обычной группы прямой URL не выдумывается;
сохранённые источники доступны через явную команду `/sources`. Новое членство в группе
не предоставляет сервису доступ к скрытой истории.

Первое сохранение чатов предлагает однократный выбор «Да / Нет». «Да» запускает разбор
до `INITIAL_MESSAGE_LIMIT=100` последних доступных сообщений каждого выбранного чата;
LLM получает сообщения не старше `MESSAGE_MAX_AGE_DAYS` (по умолчанию 90 дней), порциями
`SYNC_BATCH_SIZE`. «Нет» сохраняет временную границу отслеживания без запуска анализа:
сообщения до неё не передаются LLM даже в последующие ночи. Решение сохраняется в профиле
и не сбрасывается повторным `/start`, переподключением, ошибкой или остановкой задания.

После частичной ошибки верхняя граница исходной истории и курсор сохраняются, успешно
обработанные порции не повторяются. Дальнейший анализ выполняется по ночному расписанию,
сводка приходит утром. В боте повторного ручного запуска нет; внеплановый запуск доступен
разработчику через CLI. Новые и повторно включённые чаты начинают чтение с момента
подключения. Известные источники активных событий по-прежнему проверяются отдельно по ID.

Задание сохраняется в `analysis_runs`, запускается через asyncio task, интерфейс бота
освобождается сразу. Дублирующий запуск одного пользователя отклоняется. Статусы и счётчики
доступны в настройках, после завершения бот присылает агрегированный результат. Сырая
переписка в этом результате отсутствует. Очередь `queued` восстанавливается после рестарта,
выполнявшиеся задания становятся `interrupted` и продолжаются в следующий ночной анализ
или по явной команде разработчика через CLI.

## Что проверить настоящим Telegram-аккаунтом

Автоматические тесты используют настоящий Dispatcher/FSM aiogram и адаптеры проекта,
но подменяют Bot API и MTProto-клиент. Они не заменяют следующие проверки:

1. Получить HTTPS-ссылку через `/start` из личного чата, сверить заявку и подтвердить в боте.
   В чужом аккаунте и в групповом чате подтверждение должно отклоняться.
2. Выполнить QR-вход со второго устройства. Проверить истечение QR и отмену до сканирования.
3. Выполнить вход с одного телефона: переключиться в официальный Telegram, получить код
   способом, выбранным Telegram, вернуться в браузер. Проверить реальную 2FA, если включена.
   Коды и пароль вводит сам владелец только на HTTPS-странице, боту их не отправляют.
4. Отсканировать QR другим Telegram-аккаунтом и убедиться, что привязка отклонена, а новая
   сессия завершена. Проверить уведомление об успешном подключении правильного аккаунта.
5. Указать учебную группу, затем найти приватную группу без username и канал; проверить страницы, поиск, выбор, сохранение,
   обновление, отключение одного чата и реальную доступность ссылок на сообщения.
6. Выбрать «Да» для первого анализа с настроенным LLM, сверить отчёт с доступной историей;
   команды бота должны продолжать отвечать во время задания. Приходят статистика и сводка,
   повторное нажатие и `/sync` новый анализ не запускают. На другом тестовом профиле
   выбрать «Нет» и проверить отсутствие старой переписки в ночном анализе.
7. Перезапустить сервер и повторить доступ к чатам без ввода кода. Затем завершить сессию
   Deadline Assistant в Telegram → Устройства и вызвать проверку доступа: должно появиться
   предложение переподключиться, а существующие дедлайны остаться.
8. Переподключить аккаунт и проверить список сессий Telegram. Отключить его кнопкой и проверить
   фактический удалённый отзыв. При сетевой ошибке бот должен предложить завершить сессию вручную.

Внешний DNS, действующий TLS-прокси, доставка реальных кодов/уведомлений, ограничения
конкретного аккаунта, живой PostgreSQL и ответы выбранной LLM требуют отдельной проверки.
